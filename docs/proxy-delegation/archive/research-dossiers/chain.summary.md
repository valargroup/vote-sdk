## key_facts
- Wire tags in use: 0x02 Delegate, 0x03 Cast, 0x04 RevealShare, 0x05 SubmitTally, 0x06 CastVoteBatch, 0x07 DelegateAndCastVoteBatch, 0x08/0x0D/0x0E ceremony. 0x0A is forbidden. IsVoteTag is a contiguous 0x02..0x07 range check, so a new tag needs an explicit branch (api/codec.go:27-59).
- Canonical protobuf encoding with unknown fields rejected is enforced only for tags 0x06/0x07 (api/codec.go:143-154). Single delegate, cast and reveal tx bytes are malleable.
- Vote txs are fee-less with an infinite gas meter and are authenticated only by ZKP plus RedPallas (app/ante.go:120-183). The repo and the Caddyfile have no REST rate limiting.
- Three nullifier families are scoped by round: 0x00 gov, 0x01 VAN, 0x02 share. Key layout is 0x01||type||round||nf (x/vote/types/keys.go:98-114,210-222). Genesis accepts types 0-2 only (types/genesis.go:93-104).
- CheckNullifiersUnique checks the store only, not duplicates inside the list (keeper_voting.go:54-66). Batch handlers then call SetNullifier. Intra-message dedupe in ValidateBasic is the only guard; the gov-nullifier dedupe exists because the circuit does not constrain distinctness (msgs.go:97-106).
- AppendCommitment has no capacity check (keeper_voting.go:99-117). The tree is depth 24 (2^24 leaves, vote-commitment-tree hash.rs:13-25). EndBlock errors halt the node (module.go:441-460). ErrCommitmentTreeFull is registered but unused (errors.go:20).
- Roots are computed in EndBlock for ACTIVE rounds and stored only when changed. Any stored historical root is a valid anchor (no recency window); the ZKP2 anchor-height slot is unconstrained in-circuit (voting-circuits vote_proof/circuit.rs:169-177).
- MsgCastVoteBatch: up to 50 casts, one round and anchor, unique proposals and nullifiers. One Blake2b batch digest (SVOTE_CAST_VOTE_BATCH_SIGHASH_V1) is signed by every action. Proofs chain through SingleLeafRoot(prev van_new). Only the final VAN plus all VCs are appended (msgs.go:167-208, sighash.go:62-102, validate.go:383-448, msg_server.go:221-284).
- MsgDelegateAndCastVoteBatch uses synthetic anchor height 0, meaning SingleLeafRoot(delegation.van_cmx). Its digest binds round, van_cmx and the ordered casts. The delegation VAN is never appended, and every check runs before any write (validate.go:185-243, msg_server.go:290-354).
- Clients learn leaf positions from tx events (leaf_index, final_van_leaf_index, vote_commitment_leaf_indices) via GET /shielded-vote/v1/tx/{hash}, or by tree scan with CommitmentLeaves (5000 leaves per page). Validators expose only REST, not CometBFT RPC (deploy/Caddyfile).
- Effective size caps: REST listener 1,000,000 bytes plus handler LimitReader 1 MiB (api/handler.go:780,814). REST-to-Comet broadcast JSON is capped by Comet RPC max_body_bytes 1,000,000, so raw tx is roughly 750 KB or less [inference]. Mempool max_tx_bytes 1 MiB, block 5 MiB (app/consensus_limits.go:13), proof 15 KiB or less (keys.go:74).
- Reveal shares are capped at 256 per block, enforced in both PrepareProposal and ProcessProposal (app/vote_share_submission_proposal.go:13-89). Each vote commitment yields 16 reveals (keys.go:52). A helper worker proves about 0.58 shares/s (software-upgrades.md:446-457).
- Round lifecycle: PENDING (DKG timeouts 600 s each), then ACTIVE until absolute vote_end_time, then TALLYING (EndBlock), then FINALIZED (tally or 6 h timeout). Every vote-round message, including RevealShare, requires ACTIVE and blockTime < vote_end_time (keeper_voting.go:313-341, msgs.go:540-560). There is no delegation cutoff concept.
- The helper last-minute window is the last 40% of the round, capped at 6 h (internal/helper/store.go:1606-1619). Retries stop 5 min (minimum 30 s) before the end (retry_schedule.go:10-16,68-82).
- Activation is a coordinated Cosmovisor halt with a no-op named handler (app/upgrades.go, v1_5_0/v1_6_0). Mixed versions diverge: an old binary decode-fails unknown tags while a new one executes them. A dormant const flag was used before activation (commit 7cd8b521, flipped in 771fbdef). Upgrades must not happen during an active round or ceremony (software-upgrades.md:476-495).
- ProtocolCapabilities (query.proto:67-77, query_server.go:27-36) advertises atomic batch support and the 0x07 wire tag to clients. It does not advertise circuit or VK versions. The chain pins voting-circuits =0.12.0 (circuits/Cargo.toml).
- No round state is ever deleted. Genesis export includes all leaves, roots and nullifiers. No permissionless opaque payload is stored in state today. tx1_effects carries Orchard-format ciphertexts in tx bytes only (ffi/tx1/effects.go:10-24) [inference on layout].
- Registry precedents: MsgSetEndorser is a coordinator-action payload that creates accounts. MsgEndorseRound is a standard Cosmos tx authorized by the endorser address and whitelisted. Off-chain ADR-036 IMT acknowledgments and ed25519 PIR attestations are explicitly not consensus (docs/imt-verification.md:44-75, internal/pirupdate/attestation.go).
- The tally only consumes MsgRevealShare (ZKP3) into (proposal, decision) El Gamal accumulators (msg_server_tally_decrypt.go:22-66, keeper_tally.go:35+). It never references VANs, so proxy-delegated weight needs no tally changes if outputs are ZKP2-spendable VANs.

## design_implications
- Implement proxy delegation as a new VAN-spending circuit and message (MsgProxyDelegate) that records its input in NullifierTypeVoteAuthorityNote with exactly the same nullifier derivation as ZKP2, so a VAN can be either cast or split but never both.
- Reuse the synthetic-anchor pattern for one-transaction UX. Compose ZKP1, then split, then optionally a cast batch on the self-retained output, so intermediate VANs are never appended. The chain plumbing (SingleLeafRoot, composite digest, checks before writes) already exists.
- Treat MsgMergeVans (N VAN nullifiers in, 1 VAN out) as required for influencer-scale delegates. Without it a delegate with K delegators must create K x P ZKP2 proofs and K x P x 16 reveals. Merge ValidateBasic must dedupe input nullifiers, and padding semantics for fixed arity must be defined.
- Bound splitting in-circuit (non-re-splittable outputs, a hop counter or split-authority flag, a minimum weight per output, fixed output arity). Also add a chain-side tree-capacity guard in AppendCommitment (return ErrCommitmentTreeFull in DeliverTx) so a full tree rejects transactions instead of halting EndBlock.
- Bind every output ciphertext through the new sighash (hash each one plus count and order). Enforce canonical protobuf encoding and strict JSON for the new tags, as for 0x06 and 0x07.
- Serve encrypted payloads from state, keyed by round and leaf index, through a paginated height-range query that follows CommitmentLeaves, rather than relying on events. Public nodes expose only REST, and events require the kv indexer. Bound ciphertext size and consider deterministic deletion after finalization.
- Emit a proxy_delegate event with the nullifier and contiguous output leaf indices in the strict attribute style zcash_voting already parses, so the delegator can confirm by tx hash and recover by tree scan.
- Add a chain-enforced delegation cutoff before vote_end_time, ideally derived deterministically from created_at_time and vote_end_time so it is implicitly authenticated by the round ID and signed config. It must leave time for scan, merge, cast and 16 x P reveals within the helper's last-minute window and the 256-reveals-per-block cap.
- Consider a per-block cap on the new proof-carrying messages, modelled on MaxVoteShareSubmissionsPerBlock and enforced in both PrepareProposal and ProcessProposal.
- Ship as a coordinated upgrade (new noop vX.Y.0 handler) using the dormant-flag pattern if code merges early. Gate both the wire tag and the InterfaceRegistry registration. Extend ProtocolCapabilities with new booleans, wire tags and ideally circuit/VK identifiers. Schedule activation only between rounds.
- If split outputs keep the existing VAN preimage, ZKP2, ZKP3, the helper and the tally stay unchanged. Any new VAN field changes ZKP2 and forces a coordinated upgrade plus a new wallet prover.
- Keep the identity registry off-chain or gated (coordinator-curated payload, or endorser-signed attestations modelled on MsgSetEndorser and MsgEndorseRound). Anonymous fee-less on-chain self-registration is a spam vector, influencers cannot get accounts without coordinators, and the chain cannot verify X posts.
- Answering 'did my delegate vote' requires an explicit protocol choice, such as receipt tags published by ZKP2 or merge, plus a nullifier or tag existence query. The default nullifier design gives the delegator no visibility.

## risks_and_holes
- Tree-fill chain halt: AppendCommitment never checks capacity, EndBlock ShardTree append errors halt the node, and splits do not consume proposal_authority bits. Unbounded split chains from one VAN could fill the 2^24-leaf round tree and stop the chain.
- Weight inflation through duplicate inputs: CheckNullifiersUnique misses duplicates inside a list and circuits do not constrain distinctness. A merge or composite missing ValidateBasic dedupe could count the same VAN twice.
- Double spend through a mismatched nullifier domain: if split or merge derive VAN nullifiers differently from ZKP2, or record them under a different nullifier type, a VAN could be both voted and split.
- Ciphertext grafting: if output ciphertexts are not bound by the signature or proof, a mempool observer can submit a variant with garbage ciphertexts that lands first under the same nullifier, so the delegate never finds the VAN and the weight is lost.
- Tx malleability: non-canonical encoding allows many tx hashes for the same content, which bypasses the mempool cache and forces repeated proof verification. New tags must be in the canonical set.
- Late delegation loses weight silently. Shares are rejected after vote_end_time, and a vote commitment with only some of its 16 shares revealed is partially counted. End-of-round surges hit the 256-reveals-per-block cap and helper throughput of about 0.58 shares/s per worker.
- Influencer load: without merge, a delegate's proving and reveal load scales with delegator count (K x P x 16 reveals), and the influencer's wallet bears all of it.
- State growth: round state is never pruned and genesis export includes all leaves. Stored ciphertexts are permanent (for example 100k splits x 10 outputs x 250 B is about 250 MB), and large event attributes bloat the tx index.
- Registering new message types in the InterfaceRegistry is itself state-breaking (it changes how nested Any payloads in standard txs decode). Registration must be dormant together with the tag until the upgrade height.
- Privacy leaks: split output count, merge input count (approximate delegator count) and timing are public. Padding to fixed arity with zero-weight dummies reopens the spam and tree-growth vector unless dummies are bounded.
- No revocation or fallback: once a VAN is bound to the delegate's address, the delegator cannot reclaim it if the delegate never votes.
- Round-config authentication gap: a new stored round field such as a cutoff is not covered by round_id derivation or the signed voting config (round_id||ea_pk||pir).
- Circuit and verifying-key drift: no circuit version exists per round or in capabilities. The chain pins voting-circuits =0.12.0 while origin/main is 0.12.2, and wallet and chain provers must match exactly.
- Upgrades cannot happen mid-round; scheduling must wait for all rounds to be finalized or ceremony-failed and for helper queues to drain. Historical chain resets wipe any on-chain registry not carried into the new genesis.
- Doc drift that could mislead implementers: session-status-lifecycle.md:17-18 says TALLYING accepts RevealShare (the code rejects it); keys.go:76-79 MaxTreePosition says 2^32-1 while the tree is 2^24; ffi/zkp/verify.go calls the verifier a mock.
- REST headroom: a 50-vote delegate-and-cast is already about 78% of the effective JSON cap (estimate). Large composites such as merge plus 50 casts may exceed the roughly 750 KB raw limit.

## open_questions
- Where does the split happen: a separate VAN-split circuit (recommended, composable with synthetic anchors) or multi-output ZKP1? ZKP1 is the circuit tied to hardware-wallet TX1 signing.
- Maximum outputs per split (for example 10 delegates plus 1 self): fixed arity with padding, or variable? Is a minimum weight per output required?
- Is transitive re-delegation allowed (can a delegate re-split received VANs)? This decides the hop and split-authority encoding and the tree-growth bound.
- Is MsgMergeVans mandatory before voting? What arity (8 or 16), how are differing proposal_authority masks combined (AND, or require equality), and what is the num_ballots ceiling?
- Payload delivery: on-chain ciphertexts in a state keyspace, or off-chain (for example vizor-deeplink-server)? Which encryption key: the delegate's Orchard address or a separate key in the registry? Should ciphertext state be pruned after finalization?
- Delegation cutoff: what value, stored or derived, and how is it authenticated to Vizor?
- Can a delegator who has already voted on some proposals delegate the remaining authority (subset bitmask), and how should the wallet explain that?
- Accountability: do we accept a privacy trade-off (receipt tags, nullifier existence query) so delegators can see whether delegates voted, or offer no visibility?
- Identity registry: on-chain coordinator-curated, endorser-attested, or off-chain signed? Who runs the X verifier (ICNS-style)? Are delegate addresses global or per round, and what are Vizor's trust anchors?
- Is a revocation or fallback-to-self mechanism required if a delegate does not vote?
- Activation plan: which release (for example v1.7.0), dormant-flag merge before activation, and alignment of voting-circuits pins between chain (=0.12.0) and Vizor/zcash_voting?
- Should we add a per-block cap for the new proof-carrying messages and a REST size budget for large composites?
- Unverified: actual Halo2 verify latency per proof on validator hardware (no numbers in repo), and whether SDK gRPC-gateway block endpoints are publicly reachable through Caddy.
