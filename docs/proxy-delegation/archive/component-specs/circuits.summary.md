## key_decisions
- **Build proxy delegation as a separate additive circuit, ZKP4 (module `voting_circuits::proxy_delegation`), at K=11.** — [measured] The prototype hits the same 2,015/2,048 row high-water mark as ZKP2, a 11,008 B proof and roughly ZKP2's prove time. ZKP1, ZKP2 and ZKP3 keep byte-identical VKs, so Zodl and old Vizor are unaffected. No muxing of ZKP2's load-bearing proposal-0 gate is needed. (rejected: A mode inside ZKP2: it changes the VK for every voter, needs muxes on authority, weight and proposal slot plus a mode-gated proposal-0 gate in a 98.4%-full circuit, and gives no privacy gain because proposal_id is public. A multi-DC circuit: 16k encryptions does not fit K=11 for k>1.)
- **The DC is Poseidon5(DOMAIN_VC, round, shares_hash, 0, delegate_index). The 0 comes from a VK-baked constant cell, and DOMAIN_VC is reused rather than a new DOMAIN_DC.** — This keeps ZKP3's VK unchanged, since ZKP3 bakes DOMAIN_VC (share_reveal/circuit.rs:794-798). The namespace stays sound because ZKP2's proposal_id != 0 gate (authority_decrement.rs:407-416) acts on the same cell that feeds ZKP2's VC preimage. (rejected: A new DOMAIN_DC tag: it needs a new ZKP3 VK and a second scalar reveal verifier. Encoding the delegate in proposal_id >= 51: it collides conceptually with the authority bit semantics and needs chain range changes anyway.)
- **delegate_index is a private witness in ZKP4 and has no in-circuit range check.** — A public index would link the delegate choice to the anonymous tx, which is the whole point of B2 over B1. An invalid index only makes the DC unrevealable, which is self-harm; the chain validates the index at reveal time and the builder takes a u32. (rejected: A public index (B1-style linkage). An in-circuit registry Merkle proof: it costs rows (~900+) the circuit does not have and adds nothing because the reveal is checked anyway.)
- **The input VAN authority must equal MAX, via a constant cell in the old-VAN preimage. The successor also keeps MAX.** — The pool is routed to every proposal, so the delegated weight must hold authority on all of them. Without this, weight already cast on proposal p would count again via the pool. Keeping MAX on the successor lets the delegator keep adding DCs and then vote. (rejected: ANDing masks or per-proposal DCs: these would need pools per (delegate, proposal) and up to 50 DCs per delegate. Clearing bits on delegation: also double counts.)
- **Bounds: W_new in [0,2^30) (3-word strict lookup), each share in [0,2^30), and w = sum(shares) != 0 (inverse gate).** — The W_new check prevents the w > W wraparound inflation (measured: only this check catches it). The share bounds keep field and scalar plaintexts equal and make the nonzero check imply integer w >= 1. w >= 1 forbids free zero-weight DCs and guarantees the successor differs from the input, so in-batch VAN nullifiers are always distinct. (rejected: Allowing w=0 for padding: it yields a duplicate VAN and nullifier and gives free helper spam. Range-checking W: unnecessary, because every VAN already satisfies W <= 2^30.)
- **Add a per-VAN-chain DC slot nullifier Poseidon4(nk, TAG_SLOT+slot, round, rand) with slot in [0,16) as public input 10. The chain keeps it in a new round-scoped nullifier set.** — Without it, one registration of W ballots can mint W DCs, each causing 16 helper ZKP3s and reveals: an unbounded DoS amplification on a fee-less chain, versus 50x16 per VAN today. rand is constant along a ZKP2/ZKP4 chain, so this caps DCs at 16 per registration. [measured] It fits K=11 by reusing El Gamal track-B columns for a third Poseidon config. (rejected: A minimum DC size: the count is still proportional to W. A geometric minimum (w >= W/16): about 333 DCs and a bad UX constraint. A delegation-counter field in the VAN: changes the ZKP1 and ZKP2 VKs. A chain-only cap: DCs from one chain are unlinkable across txs.)
- **Reuse ZKP3 unchanged for DC reveals with proposal_id=0 and vote_decision=delegate_index. After private vote lands, keep the v1 scalar ZKP3, byte-identical, as the pool-reveal path.** — [code] ZKP3 has no lookups or range checks on these values. [measured] Reveals pass for index 1234 and u32::MAX and fail for a wrong index or proposal. Pools have no secret choice to hide, so a scalar format is right. (rejected: The vector ZKP3 with D=1: 128 encryptions per DC (a ~57.7 KiB ZKP1.5-class proof) and no slot for delegate_index in the VC_v2 preimage.)
- **Sequencing: ship proxy delegation first (voting-circuits 0.13.0, adding ZKP4 only), or bundle it with private vote. The private-vote merge must retain DOMAIN_VC, the v1 share commitment and shares hash, prove_elgamal_encryptions and the v1 ZKP3 module.** — Each circuit's VK then changes at most once. ZKP4 and pool-reveal depend only on v1 primitives, which the branch currently deletes (pv:CHANGELOG.md:53-58). (rejected: Defining ZKP4 on v2 primitives (DOMAIN_VC_V2, the bridge): this would force a second ZKP4 bump or a ZKP1.5-sized proof. Private vote first: workable, but it resurrects deleted code and chain verifiers.)
- **Choose B2 (helpers and unchanged ZKP3) over B1 (public in-tx slots).** — B1 is cheaper ([measured] 1 proof of 1,662 rows for 10 slots, no reveals). But it gives an EA-key holder the exact per-delegation amounts and full allocation profile, and shows every observer the delegate set linked to one tx. That conflicts with decision 4. (rejected: B1 as the default. Keep it only as a possible opt-in fast path if the owner accepts EA-visible amounts.)
- **DC secrets come from a new PRF stream: domains 0x10-0x14 with context (round, 0, van_old, share_index, delegate_index, delegated_ballots).** — Secrets stay deterministic for crash recovery, and a re-planned DC from the same VAN can never reuse an El Gamal nonce for a different plaintext. 0x05 and 0x06 are avoided because private vote claims them. (rejected: Reusing the vote PRF domains with proposal_id=0: sound, but it lacks the (d, w) binding.)
- **Make the builder APIs ballot-denominated, with ballot variants for ZKP2 as well.** — After a ZKP4 the remaining weight is W-w ballots. Today's ZKP2 builder takes zatoshi and floor-divides (builder.rs:782), which is error-prone for chained successors. (rejected: Passing remaining_ballots*12,500,000 into the zatoshi API: it works, but it is a latent unit bug.)

## baseline_challenges
- HIGH (fix in ZKP4): the baseline places no per-VAN limit on the number of DCs. With only 1 <= w <= W, one registration of W ballots can mint up to W DCs across many batches. Each DC triggers 16 helper ZKP3 proofs and 16 reveal txs (256 reveals per block cap), which is an unbounded helper and reveal DoS amplification on a fee-less chain; a VAN today is capped at 50x16 reveals. Fix: add condition C14, a DC slot nullifier Poseidon4(nk, tag('proxy delegation slot')+slot, round, van_comm_rand) with slot in [0,16), as public input 10. rand is constant along a ZKP2/ZKP4 chain, so this caps DCs at 16 per registration per round. [measured] It fits K=11 at 2,015 rows with an 11,008 B proof.
- HIGH (chain dependency): CheckNullifiersUnique (vs/x/vote/keeper/keeper_voting.go:54-66) does not reject duplicates inside one message list. Two ZKP4 actions in one batch that reuse a slot index would produce the same slot nullifier and pass. The check must reject intra-batch duplicates for the VAN nullifier set (0x01) and the new slot set (0x03) before proxy delegation is enabled.
- MEDIUM (soundness note plus test): ZKP2's proposal_id != 0 inverse gate (authority_decrement.rs:398-416) is documented as defense-in-depth but becomes load-bearing. Without it, ZKP2 could clear sentinel bit 0 and emit VC(0, d) while keeping full weight for all 50 proposals, which double counts into Pool[d]. Re-document it, keep the proposal_id_zero_fails test (vote_proof/circuit.rs:2741) as a proxy-delegation soundness test, and require every ZKP2 rewrite (the private-vote compact ZKP2, adam/lookup-free-authority-prototype) to keep it.
- MEDIUM (sequencing): 'ZKP3 unchanged' is true only while the v1 scalar primitives exist. The private-vote branch removes DOMAIN_VC as a live tag, the 5-input share commitment, the two-level shares hash and prove_elgamal_encryptions (pv:CHANGELOG.md:53-58, pv:src/domain_tags.rs:25-31, pv:src/gadgets/elgamal.rs). Fix: the merge keeps them and keeps the v1 share_reveal as a byte-identical, fingerprint-pinned pool-reveal circuit. DOMAIN_VC is re-documented as live for proposal-0 pool commitments.
- MEDIUM (non-circuit blockers missing from the baseline): proposal 0 and decision >= 8 are rejected in chain MsgRevealShare.ValidateBasic (vs/x/vote/types/msgs.go:245-250), the helper validatePayload (vs/internal/helper/api.go:771-778), and zcash_voting build_share_payloads and VoteShareWire::validate (zv/src/vote_commitment.rs:32-33, zv/src/wire_codec.rs:303-313). Each needs a capability-gated proposal-0 path. None of these changes affects a VK.
- MEDIUM (product, integrator): decision 4 (per-delegate totals hidden) is not fully achievable with public routes plus published per-option tallies. When a delegate skips proposal P, turnout(P') - turnout(P) approximates Pool[d] whenever direct turnout is stable across proposals. Decrypting an explicit 'unrouted' bucket would leak the sum exactly. Mitigation: encourage or require delegates to route every proposal, and document the residual inference.
- LOW (refinement): the baseline's 1 <= w <= W must be stated as concrete constraints. Use W_new = W - w range-checked to [0,2^30), which is the only check that stops w > W inflation, and w = sum(shares) != 0 via an inverse gate. The DC share PRF should use dedicated domains bound to (delegate_index, w).
- LOW (helper privacy): helpers learn each DC's delegate index and leaf position (and hence its tx), as they do for votes today. After private vote lands, votes stop leaking their choice to helpers but DCs still leak the delegate. Document this as a known asymmetry.

## cross_component_contracts
- PROVIDES to chain: the ZKP4 verifier. VK = keygen_vk(Params::new(11), proxy_delegation::Circuit::default()). It takes 11 public inputs (32 B each, FFI buffer 352 B) in this order: van_nullifier, r_vpk_x, r_vpk_y, vote_authority_note_new, delegation_commitment, vote_comm_tree_root, vote_comm_tree_anchor_height (transcript-bound only), voting_round_id, ea_pk_x, ea_pk_y, dc_slot_nullifier. New FFI entry point sv_verify_delegation_commitment_proof. Proofs are <= 11,008 B, under the 15 KiB MaxProofSize.
- PROVIDES to chain/helper/client: the native preimage formulas. DC = Poseidon5(1, round, shares_hash, 0, delegate_index). The VAN nullifier is identical to ZKP2's. dc_slot_nullifier = Poseidon4(nk, tag('proxy delegation slot')+slot, round, rand). share_nf = Poseidon4(tag('share spend'), DC, share_index, blind). Frozen vectors are in spec §8.4.
- PROVIDES: ZKP3 unchanged. A pool reveal is a standard ZKP3 with proposal_id = 0 and vote_decision = delegate_index (u32 encoded as Fp via u64). The ZKP1, ZKP2 and ZKP3 VK fingerprints stay byte-identical in the release that adds ZKP4.
- PROVIDES to client (zcash_voting): build_delegation_commitment_proof, derive_proxy_delegation_transition, rederive_delegation_shares, delegation_commitment_hash, dc_slot_nullifier, delegation_share_nullifiers, share_reveal::build_pool_share_reveal, and ballot-denominated ZKP2 builder variants. DC secrets are deterministic from (sk, round, van_old, delegate_index, delegated_ballots, layout).
- REQUIRES from chain: verify the first action against the real root at its anchor height (or SingleLeafRoot(van_cmx) after ZKP1, synthetic height 0); verify each later action against SingleLeafRoot(previous action's vote_authority_note_new); take ea_pk and round from authenticated round state; decompress r_vpk; verify one batch-wide sighash signature per action.
- REQUIRES from chain: ZKP4 van_nullifiers go into the SAME VAN nullifier set as ZKP2 (type 0x01). dc_slot_nullifiers go into a new round-scoped set (e.g. type 0x03). Both checks must reject intra-batch duplicates; fix CheckNullifiersUnique.
- REQUIRES from chain: statelessly reject any DC action that follows a cast in the same batch (fail fast; the circuit enforces this anyway); policy cap of 10 DCs per batch; append the final successor VAN once, then the DC leaves, then the VC leaves in action order; expose DC leaf indices in the response or events; add a tree-capacity check in AppendCommitment.
- REQUIRES from chain (reveal path): in proxy-enabled rounds, accept MsgRevealShare with proposal_id = 0 and vote_decision = delegate_index. Index validity is monotone (index < registry length) and must never fail because of a later revocation. Accumulate into TallyKey(round, 0, d). Keep rejecting MsgCastVote with proposal_id 0. After private vote, accept scalar reveals only for proposal 0.
- REQUIRES from chain (tally): exclude proposal-0 pools from decryption and completeness checks. At ACTIVE->TALLYING, add Pool[d] to agg[p][route(d,p)] for each routed (d, p); unrouted means abstain.
- REQUIRES from registry component: delegate_index is a u32, append-only and never reassigned. Key rotation keeps the index, because the DC binds the index, not the key.
- REQUIRES from chain capabilities: advertise proxy_delegation_v1, the ZKP4 VK fingerprint and the slot cap (16), so that clients can refuse to prove against a mismatched VK.
- REQUIRES from helper server (vote-sdk internal/helper): accept payloads with proposal_id = 0 and a u32 decision in proxy-enabled rounds. The vcHash-vs-tree-leaf check stays as is. For proposal 0 the choice validator becomes a registry lookup. Scheduling, including single-share last-moment mode, is unchanged.
- REQUIRES from client (zcash_voting/Vizor): plan every DC for a VAN before any cast on it; persist (delegate_index, w, slot, single_share) intents; allocate slots 0..15 sequentially per VAN chain and recover them via dc_slot_nullifier queries; add a DC share-payload path that bypasses validate_proposal_id and the MAX_VOTE_OPTIONS check; evict the ZKP4 proving key after use on mobile (~140 MiB keygen peak).
- REQUIRES from private-vote work (voting-circuits): retain DOMAIN_VC, the v1 share_commitment and shares_hash, prove_elgamal_encryptions plus SpendAuthGFixedBase30Config, and the v1 share_reveal module (renamed pool_reveal), with its VK fingerprint pinned to today's value. Keep the proposal_id != 0 gate in the compact ZKP2. Do not reuse PRF domains 0x10-0x14.

## open_questions_for_owner
- Hard cap on DCs per registration (VAN chain) per round: 16 (one 4-bit check, as measured) or exactly 10 (one extra short check, still K=11)? Recommendation: hard cap 16 in the circuit, product and UI cap 10 per batch and per delegator. The extra slots let users add a delegate later in the round without a circuit change.
- Minimum delegation size: the circuit enforces w >= 1 ballot (0.125 ZEC). Should a larger minimum (e.g. 8 ballots = 1 ZEC) be baked in? Recommendation: keep 1 ballot in the circuit. The slot cap already bounds spam, and any larger minimum can be a UI default.
- What does 'did not vote' mean for pooled weight, given the turnout-differencing leak of pool totals? Recommendation: keep 'unrouted = abstain, excluded', but strongly encourage delegates to route every proposal (UI nudges, an explicit abstain option counted like a vote), and document that per-delegate totals can be inferred statistically when delegates skip proposals.
- Release order relative to private vote choice. Recommendation: ship proxy delegation first as voting-circuits 0.13.0 (ZKP4 only, ZKP1/2/3 VKs unchanged), or bundle both. Either way, make it a merge requirement on the private-vote branch that the v1 scalar primitives and ZKP3 (as pool reveal) are retained byte-identical.
- B1 as an optional fast path? Recommendation: no. B2 only, because B1 exposes exact per-delegation amounts to any holder of the full EA key and links each delegate set to a single tx.

## risks
- ZKP4 sits at 2,015/2,048 rows (27 usable rows of headroom on the primary track). Any future condition, such as a registry or delegate-key binding or a stronger delegate_index check, likely forces K=12, about 2x prove time. Keep further logic out of the circuit or plan for a third Poseidon track.
- Private-vote merge risk: the branch deletes the exact v1 gadgets ZKP4 and pool reveal depend on. Without a merge gate (VK-fingerprint tests for ZKP4 and pool_reveal), a later refactor could silently break proxy delegation or force a second VK bump.
- The load-bearing ZKP2 proposal_id != 0 gate could be dropped by a future authority-chip rewrite; a lookup-free authority prototype branch already exists. That would allow pool double counting. Mitigation: make the proposal_id_zero_fails test non-ignored and label it a proxy-delegation soundness test.
- Until the chain rejects intra-batch duplicate nullifiers, the slot cap can be bypassed inside one batch (at most 10 DCs per batch by policy, but repeated slots would be possible).
- Mobile cost: each DC is one ZKP2-equivalent proof (~2 CPU-s on an M4 Max including overhead per the zcash_voting benchmark doc), so 10 DCs take many seconds on phones within a 15-minute foreground-only window. Keeping both ZKP2 and ZKP4 proving keys in memory roughly doubles key RAM (~136 + 140 MiB peak at keygen).
- Privacy: helpers learn the DC-to-delegate link and the tx position. Single-share last-moment DCs reveal the exact w to any EA-key holder. Observers see the DC count k per batch. Per-delegate pool totals are statistically inferable from public routes plus turnout differences.
- Reveal throughput: each DC adds 16 reveals (or 1 in single-share mode) under the 256-per-block cap. With the slot cap, the worst case is 256 reveals per registration, compared with 800 for votes, so ordinary load rises but stays bounded.
- Timing figures were measured on a shared, loaded M3 Ultra (load average 12-38). They are reliable as relative comparisons (ZKP4 ≈ ZKP2), not as absolute numbers. Mobile was not measured.
- The DC slot-nullifier tag text and the PRF domain bytes are protocol constants. Changing them after release breaks the VK (tag) or recovery determinism (PRF), so pin them in domain_tags tests before the first release.
