## key_facts
- Vizor ships on 5 platforms. HTTPS deep links (link.vizor.cash) are handled only on iOS and Android; desktop runners register no handler (vizor:lib/src/core/navigation/incoming_link_dispatch.dart:4-7; dls:src/config.ts:15-28). AGENTS.md:303 still says only iOS, Android and macOS.
- Mobile Dart work is foreground-only; desktop keeps running while hidden (vizor:lib/src/core/layout/app_process_work_policy.dart:4-17). Mobile auto-locks after 15 minutes in the background (core/security/background_auto_lock_host.dart:14). There is no push and no voting background task.
- Voting hotkeys are random, one per account per round, phone-held even for Keystone and Ledger accounts, under secure-storage key zcash_account_voting_hotkey_{uuid}_{roundId}. They are app-encrypted and readable only while unlocked (core/storage/app_secure_store.dart:59,358-375,729-738). They cannot be recovered from the seed or UFVK (rust/src/wallet/voting/README.md:42-50; docs/voting-participation.md:146).
- Delegation (ZKP1) is currently driven by ballot intents: the SDK plans a bundle's delegation only while that bundle has a vote to cast, and Vizor records intents before branching (providers/voting/voting_submission_job_provider.dart:669-708). The SDK can submit delegation atomically with the vote batch via MsgDelegateAndCastVoteBatch (chain:proto/svote/v1/tx.proto:105-113).
- open_pipeline binds the SDK DelegationPipeline to the wallet's own hotkey only (rust/src/wallet/voting/delegation.rs:86-139). Bridge signer kinds are only Mnemonic, KeystoneStored and KeystoneProvided (rust/src/api/voting_session.rs:82-89).
- The SDK (5.1.1-rc.3, pinned at rust/Cargo.toml:129-130) already has a full-weight custody handoff: VotingHotkeyTargetV1 (round-bound, address_index 0), prepare_delegation_bundle_for_target, export_delegation_capability and import_delegation_capability, plus advance_imported_delegation (zv:docs/exporting-to-external-software.md:38-160; zv:zcash_voting/src/wire.rs:158-171). Vizor exposes none of it except the NextStepKind.advanceImportedDelegation enum value.
- import_delegation_capability accepts exactly one complete package per (round, wallet_id) and rejects locally constructed or conflicting bundle state (zv:zcash_voting/src/delegation_capability.rs:380-457). Vizor's wallet_id is the account UUID (rust/src/api/voting_session.rs:259-260).
- Keystone and Ledger show an SDK-built memo, 'I am authorizing this hotkey managed by my wallet to vote on {round}. Amount: X ZEC.', in the delegation PCZT output to the hotkey address (zv:zcash_voting/src/delegate.rs:2426-2464; action.rs:565-578). Vizor mirrors the memo on screen (voting_status_screen.dart:1695-1800).
- Bundles cap at 5 notes (governance.rs:22). The privacy trim targets at most 2 bundles per holder and may drop up to 1% (max 1,000 ZEC) of weight (zv:zcash_voting/src/note_bundling.rs:23-52). Weight is quantized to 0.125 ZEC (governance.rs:15).
- Vizor's participation reader verifies Tendermint-signed IAVL proofs only for governance-nullifier keys 01 00||round||gov_nf (rust/src/wallet/voting/participation.rs:18-23,94-101). VAN nullifiers are stored on chain at 01 01||round||van_nf (chain:x/vote/types/keys.go:100-114).
- Vizor loads no remote images (no Image.network or NetworkImage in lib/src). Avatars are 15 bundled PNGs (core/profile_pictures.dart:1-71). There is no X/Twitter or name-service code, and no image proxy.
- Voting HTTP uses NetworkHttpClient, which follows the Tor/direct route policy. Tor is opt-in, defaults off and fails closed. Tor allows GET and POST only (core/network/network_http_client.dart:25-34,420-422; providers/network_privacy_provider.dart:79-80; services/voting/voting_http.dart:56-125).
- vizor-deeplink-server is a stateless Lambda+CloudFront gateway. It has an exact route allowlist (/ and /payment-links/open), and its charter forbids a database, analytics or remote assets. CSP is img-src 'self' and connect-src 'none'. OG/Twitter card tags exist only for the static Gift Card PNG (dls:README.md:9-12,70-90,171-173; src/routes.ts:10-19; src/handler.ts:15-24; src/page.ts:226-243). AASA and assetlinks already claim all paths (src/associations.ts:3-33).
- There is no analytics or telemetry SDK. Voting observability runs in debug builds only (rust/src/wallet/voting/observability.rs:30). Rollout levers are: compile-time dart-defines; a version-keyed remote JSON (swap-enabled.json, core/config/swap_remote_enable_config.dart:10-31); [TEST]-prefixed hidden rounds (providers/voting/voting_round_visibility_provider.dart:12-17); and the dynamic-config vote_protocol gate (SDK accepts v0 and v1, zv:zcash_voting/src/config/mod.rs:82,102).
- Bench numbers: ZKP2 p50 is 0.117 to 0.214 s. A 37-proposal, 3-bundle round took about 58 s of drive plus about 523 s of helper delivery work. Vote steps are round-serialized (zv:stage-bench/README.md:198-227). There is no ZKP1 timing figure.
- Wallet-link already provides an encrypted relay pattern: AES-256-GCM envelopes, package create/status/revoke, and a build-time backend URL (features/wallet_link/wallet_link_config.dart:1-6; services/wallet_link_api_client.dart; services/wallet_link_completion_crypto.dart:9-30).

## design_implications
- Proxy delegation must be a delegation step that runs with no ballot intents. The SDK planner and RoundPlanView need a first-class outbound proxy-delegation record and step. Vizor needs a new job, modeled on VotingSubmissionJobNotifier, because _run requires a draft and records intents first (voting_submission_job_provider.dart:521-708). Any new NextStepKind must be classified in voting_resume_plan.dart:60-71.
- Delegate addresses need a stable, publishable identity. VotingHotkeyTargetV1 binds vote_round_id, and Vizor hotkeys are per-round random and unrecoverable. Choose between (a) a long-lived delegate key with backup/export and a protocol-level per-round derivation, or (b) a per-round publish step that every delegate must perform after each round is created.
- The N:1 influencer case is impossible on the current SDK import path (one capability per round per wallet_id, no mixing with own bundles). The SDK needs a per-delegation scope or separate wallet_id namespaces, and Vizor's open_voting_db(db_path, account_uuid) scoping must change.
- Without protocol support for consolidating received VANs, a popular delegate must cast one ZKP2 per received VAN per proposal, in the foreground on mobile. This does not scale (about 37k proofs for 1,000 delegators × 37 proposals). The circuit plan should include VAN merge/consolidation or a delegate-side aggregate.
- Percentage splits across up to 10 delegates cannot be done by assigning note bundles: notes are coarse, the privacy trim targets at most 2 bundles, and splits are quantized to 0.125 ZEC. A VAN-split circuit is required. Each split is a separate chain transaction, so the UX needs a sequential, resumable N-step progress screen.
- Hardware confirmation needs new device-visible text. The SDK memo must say proxy delegation to {handle/address} with the amount instead of 'this hotkey managed by my wallet'. The output recipient becomes the delegate's address, so the Vizor review screen should show the same address and handle the device shows.
- 'Did my delegate vote?' cannot be answered with today's primitives. The delegator cannot compute the delegate's VAN nullifier. Vizor's light-client IAVL verifier (participation.rs) could prove a type-0x01 nullifier key or a new delegator-computable tag key if the protocol adds one, so a circuit-level tag (or a signed delegate attestation) must be decided up front.
- Delegated-VAN openings must reach the delegate over a confidential, authenticated channel unless the protocol puts encrypted openings on chain. The wallet-link relay (AES-GCM envelopes plus a Vizor backend) is the closest existing pattern, but it needs a production URL and an availability/retention design that lasts through round close.
- Directory and avatars must respect Vizor's privacy posture: no direct pbs.twimg.com fetches. Fetch through NetworkHttpClient (Tor-aware, GET/POST) from a Vizor-hosted directory/avatar proxy (e.g. functions.vizor.cash) and render with Image.memory. Never use Image.network, which bypasses the route policy.
- Delegate profile links (link.vizor.cash/d/<handle>) need deliberate additions to both allowlists: server routes.ts/page.ts and wallet vizor_deep_link.dart/incoming_link_dispatch.dart. Per-delegate OG cards conflict with the gateway's no-DB/no-remote-asset charter. Desktop (3 of 5 platforms) cannot open the app from HTTPS links, so in-app search and paste/QR fallbacks are required.
- Ship behind the dynamic-config vote_protocol bump (old builds automatically refuse), pilot with [TEST] rounds and the 'Show test rounds' toggle, and optionally add a version-keyed remote flag modeled on swap-enabled.json. Vizor has no analytics, so success metrics must come from chain-side aggregates.
- Every new durable artifact (outbound proxy records, delegate keys, imported openings, directory caches) must join account deletion and reset cleanup (account_provider.dart:1745-1790; voting.rs delete_voting_account_state:1029-1045). Background work must register with the share-tracking/destructive drain (AGENTS.md:342-352), and all new UI and network roles must follow the voting README route-table audit (rust/src/wallet/voting/README.md:311-341).

## risks_and_holes
- The 'Already used for this round' and Home-hide logic (voting_polls_screen.dart:504-507; docs/voting-participation.md:141-146) will misreport a wallet that proxy-delegated all of its weight unless an outbound delegation record exists. After reinstall or seed restore that record is gone, so the user loses delegate status and any tracking.
- Loss of the delegate's hotkey loses all weight delegated to it for the round (no seed recovery, README:46-48). For influencers this is catastrophic, and hotkeys do not move between devices via wallet-link.
- An influencer with zero shielded ZEC is 'Not eligible' under current gating (voting_state.dart:147-150; voting_submission_job_provider.dart:590-640). The delegate path must bypass own-note eligibility without weakening checks for normal voters.
- Splitting into many delegation submissions multiplies on-chain submissions per holder. That undoes the privacy trim's at-most-2-bundles goal (note_bundling.rs:31-37) and makes delegators stand out unless the circuit hides split count.
- VAN splits after partial self-voting inherit the cleared proposal bits (book partial-delegation.md: the bitmask is preserved). If the delegator votes before delegating, the delegate silently gets no authority on those proposals. The UI must enforce or explain the ordering.
- The Keystone screen will show only a raw delegate address. A compromised phone could substitute a different address while showing the right handle in Vizor's UI. Mitigation depends on the device showing the address or handle and on the user cross-checking it against a published profile.
- Successive sequential splits (N chain transactions) plus ZKP1 proofs on mobile have to run in the foreground. Backgrounding stalls them, and auto-lock after 15 minutes interrupts. Recovery must be resumable mid-chain without double-spending VANs.
- Delegated-weight discovery: if openings are delivered off-chain and the relay drops them before the delegate imports, that weight is unusable for the round (exporting-to-external-software.md:113-118). There is no public-chain-only recovery in v1.
- Fetching X avatars or profile data directly leaks the user's IP to X/CDN and bypasses Tor if done with Image.network. Any server-side X verification (ICNS-style 'post a tweet') needs a backend that reads X, whose API access and cost are external dependencies.
- App-store risk (inference): an in-app searchable directory of user-generated influencer profiles may trigger Apple and Google UGC requirements (report/block/moderation). Vizor already has iOS-specific feature kill-switch precedent for swap (swap_remote_enable_config.dart).
- The local vizor-deeplink-server checkout only accepts #v1/#v2 fragments (src/page.ts:132), while the wallet documents v3 Gift Card links (docs/compact-gift-links.md). The checkout may be stale; verify the deployed version before extending it.
- Today all foreground voting traffic shares configured API servers for chain, helper and tree (voting_session_provider.dart:1804-1818). A new directory, relay or avatar host is a new network role that must be added to the route table and service tests (README:311-341), or it may slip outside the Tor policy.

## open_questions
- Should the delegate key be long-lived across rounds (published once with the X handle) or per-round (published after each round is created)? If long-lived, how is it backed up and recovered, given current hotkeys are explicitly unrecoverable, and can Keystone/Ledger-only users be delegates?
- How do delegates learn about delegations: on-chain encrypted VAN openings that the hotkey can trial-decrypt, or an off-chain encrypted mailbox (a wallet-link-style relay on functions.vizor.cash)? Who runs it, and how long is data retained?
- Will the circuit support VAN consolidation/merge so a delegate with many delegators casts about one ZKP2 per proposal? If not, what delegate scale is acceptable?
- What exactly should 'did my delegate vote?' reveal: per-proposal yes/no, timing, nothing until tally? Is a delegator-computable spend tag acceptable given the linkability it creates between delegator and delegate?
- Can a delegate also vote their own notes in the same round from the same Vizor account (the current SDK import forbids mixing)? Can a delegate re-delegate (the book allows it)?
- Is revocation or re-delegation within a round required (e.g. the delegate is inactive near the deadline)? Since the VAN is consumed, can the delegator reclaim weight?
- Split granularity: free percentages (quantized to 0.125 ZEC) or fixed presets? Maximum delegate count (10?), and must 'keep some for myself' work with zero self-votes?
- Directory: where does it live (Vizor backend, signed entries in token-holder-voting-config, on the vote chain), how are X claims verified (post containing a signed delegate-key statement, checked by whom), and how are impersonation, handle changes and takedowns handled?
- Avatars: cache X avatars server-side behind a Vizor proxy (one origin, Tor-friendly), or use bundled avatars only and show the handle?
- Profile links: add a link.vizor.cash/d/<handle> route with a per-delegate OG card (requires relaxing the gateway's no-DB/no-remote-asset charter), or keep links data-in-fragment with a generic OG image? Desktop users cannot open the app from these links, so what is the desktop fallback?
- Hardware review: what exact memo text and recipient display do Keystone firmware and the Ledger Zcash app show for a proxy-delegation PCZT, and do firmware updates need coordination?
- Which Vizor release lever gates the feature: a vote_protocol bump in dynamic config (forced upgrade for that round), [TEST] rounds only, or an additional remote JSON flag? Is a Vizor-only round acceptable while Zodl stays on v1?
- Is the vizor-deeplink-server local checkout (b325f07, 2026-09-16) current with production? It lacks v3 Gift Card fragment support that the wallet documents. Also, Vizor's lib/rust/docs snapshot excludes ios/, android/, macos/ and repo-root files (FIGMA-AI-FIX.md, design_suggestion, copy CSVs), which I could not verify.
