## key_decisions
- **ZIP-A (PR 1200) is the base protocol ZIP. Proxy delegation goes in a separate companion ZIP (ZIP-PD), and identity and registry in a third (ZIP-DR). ZIP-A only gets small hooks: proposal-0 reservation, DC leaf kind, the VAN-consumption rule, corrected rationale, and a no-receipt-freeness non-requirement.** — ZIP-A matches the code (y-coordinate share commitments, sighashes, per-vote secrets) and is MUST-heavy. A separate optional extension lets Zodl and other wallets claim base conformance without implementing proxy delegation, and keeps ZIP-A review stable. (rejected: ZIP-G as the base: it drifts further from code, though its round-ID, EA-key and firmware sections get ported. Folding proxy delegation into ZIP-A: it couples an optional feature with different trust assumptions to the core spec and reopens PR 1200 review.)
- **Advertise proxy delegation through additive channels only: chain VoteRound.proxy_delegation params (outside the round-id preimage), new ProtocolCapabilities fields including circuit VK fingerprints, and a new optional dynamic-config key extensions.proxy_delegation_v1 signed per round. Never bump supported_versions.vote_protocol or tally for it.** — Zodl reads the same dynamic config and hard-fails on an unknown vote_protocol (zodl-ios docs/voting-service-discovery.md; WAPI:719-722), but ignores unknown JSON keys. A version bump would lock Zodl out of all rounds. (rejected: A vote_protocol bump (breaks Zodl globally). A per-round auth_version bump (Zodl marks the round unknownAuthVersion, so Zodl users could not vote in proxy rounds). Binding params into voting_round_id (changes the round-id derivation for every client).)
- **Add an in-circuit minimum delegation weight: w - min_dc_ballots in [0, 2^30), with min_dc_ballots as a ZKP4 public input checked by the chain against a round parameter (recommended default 8 ballots = 1 ZEC).** — With w >= 1, one VAN can mint W fee-less DCs, each costing 16 helper proofs, one tree leaf and reveal-cap slots near the deadline. A public input keeps the policy adjustable per round without a VK change. (rejected: A circuit constant (any change is a VK bump). A client-only policy (unenforceable). A per-lineage DC counter in the VAN (changes the ZKP1/ZKP2 VKs).)
- **Pool shares reuse MsgRevealShare (0x04) with a proposal_id == 0 branch. The branch emits a distinct reveal_pool_share event, does not touch ShareCount, and counts toward the 256/block cap. Tag 0x04 becomes the permanent scalar-reveal path.** — The ZKP3 circuit and proof bytes are identical, so a new tag adds nothing. Keeping 0x04 scalar lets V2 vector reveals take a new tag while pool reveals keep working in V2 rounds. A distinct event protects naive consumers and old clients. (rejected: A new reveal tag for pools: duplicates the handler and complicates the per-block cap. Reusing the reveal_share event and ShareCount for proposal 0: leaks a phantom proposal 0 to old clients and dashboards.)
- **Ship B2 before the private-vote-choice redesign (V2), as two separate activations. Make preservation of the scalar ZKP3 (as pool_share_reveal, with VK pinned to today's ZKP3) and of the V1 shares_hash/El Gamal gadgets acceptance criteria for the V2 PR.** — B2 is additive: it adds one VK (ZKP4) and changes no existing VK, so Zodl is unaffected. V2 changes ZKP2 and ZKP3 VKs, adds a 57.7 KiB proof that exceeds the 15 KiB cap, and forces a Zodl update. The V2 branch currently deletes the scalar ZKP3 that B2 depends on. (rejected: One combined VK bump: B2 has no existing-VK bump to combine, and bundling makes B2 hostage to V2's review, cap change and Zodl release. V2 first without preservation: breaks DC reveals entirely.)
- **One new mixed-action batch tag (0x09 proposed): optional ZKP1, then 1..max_dc_actions_per_tx DCs, then 0..50 casts, chained by single-leaf roots and signed over one SVOTE_VOTE_ACTION_BATCH_SIGHASH_V1 digest. A chain-advertised max_vote_tx_bytes budget makes the client split oversized batches.** — It generalizes the proven 0x06/0x07 pattern, keeps intermediate VANs out of the tree, and allows one-transaction UX. ZKP1 plus 10 DCs plus 50 casts would exceed the 1 MiB REST limit, so a byte budget is required. (rejected: Separate DC-only transactions: timing-linkable to ZKP1 and more submissions. An unbounded batch: rejected at REST or by mempool size limits.)
- **The on-chain registry stores only the DK, an attestation digest, status and key history. X identity data lives in an off-chain binding list (append-only, signed, hash-pinned per round) plus a mutable profile overlay (handle, pfp, bio, featured), served whole from two mirrors.** — It keeps X content out of immutable chain state and git (X 24 h deletion duty) while keeping index-to-DK authentication on chain for routes. Downloading the whole snapshot avoids leaking delegation intent. (rejected: Handles and pfps on chain or in git (compliance violation, cannot be delisted). Per-delegate lookups (leak interest). Handle-keyed identity (recycling and takeover).)
- **Delegator verification uses share-nullifier existence (IAVL-provable under nullifier type 0x02) plus public routes. No new delegator-recognizable tags or circuits.** — By ZKP3 soundness, a share nullifier derived from the DC can only be revealed with public (0, d), so existence implies the share was added to Pool[d]. Vizor already verifies IAVL proofs for nullifier keys. (rejected: Successor-VAN tracking (applies to VAN transfer, not B2). Delegator-computable spend tags (new circuit cost, no benefit here).)
- **No new chain deadline. Proxy transactions, pool reveals and routes are accepted until vote_end_time; routing happens in the ACTIVE to TALLYING EndBlock before any partial decryption. Wallets apply a soft cutoff at vote_end_time - last_moment_buffer and a hard client cutoff at vote_end_time - 30 min.** — Finality (owner decision 2) removes the need for a delegate deadline or override window. Leaving chain timing unchanged keeps Zodl's behavior identical, and client cutoffs protect reveal completeness. (rejected: Namada-style delegate deadline plus override window (needs override, which owner decision 2 rejects). A chain delegation cutoff (new consensus timing field with no safety benefit).)
- **Dormant-flag merges in vote-sdk with a single coordinated v1.7.0 activation between rounds. voting-circuits 0.13.0 is pinned identically by the chain and Vizor-bound clients, and VK-fingerprint non-regression for ZKP1/2/3 is a release gate.** — This follows the proven atomic-batch pattern (commits 7cd8b521, 771fbdef). It removes today's 0.12.0 vs 0.12.2 pin skew, and the fingerprint gate guarantees Zodl and custody-voter remain valid. (rejected: Merging live behind runtime config (mixed-version divergence). A separate upgrade for the tree-capacity guard (two halts instead of one).)
- **Ship a thin follow-mode v0 (delegate directory plus DK-signed voting guides plus copy-to-ballot) only as a by-product of the B2 identity stack, one round ahead if the verifier MVP is ready, and never gating B2.** — It de-risks the most externally fragile part (X API, ToS, moderation, pfp pipeline) in production, seeds delegate supply, and remains useful after B2 as the privacy-maximal, override-capable option. (rejected: A standalone follow engine with its own identity format (throwaway work). Skipping v0 entirely (all identity risk lands at B2 launch).)
- **User-facing naming: "Delegate" is reserved for proxy delegation. ZKP1 is renamed to "voting authorization" in Vizor copy. Spec terms: registration, proxy delegation, delegator, delegate, delegate key, delegation commitment, delegate pool, route, share submission.** — Vizor copy currently calls ZKP1 a "voting delegation" (voting_status_screen.dart:1289,1345; voting_session_provider.dart:1303), and the book uses "delegation" for share submission too. Three meanings of one word would confuse users and implementers. (rejected: Calling the feature "proxy" in the UI (jargon). Keeping "delegation" for ZKP1 (collides with the new feature).)

## baseline_challenges
- HIGH (compatibility): any rollout plan that gates proxy delegation by bumping supported_versions.vote_protocol or tally in the shared dynamic config would lock Zodl out of every round. Zodl fetches the same dynamic config (CFG prod/dynamic-voting-config.json; ZI docs/voting-service-discovery.md) and MUST reject unknown versions (WAPI:719-722); the Vizor dossier proposed such a bump. Fix: advertise via chain round params plus ProtocolCapabilities plus an optional extensions.proxy_delegation_v1 key that old decoders ignore (Swift Codable and Rust serde without deny_unknown_fields). Amend WAPI version handling so additive extensions never bump majors. Keep proxy rounds at their current auth_version.
- HIGH (cross-workstream coupling): the baseline assumes ZKP3 stays unchanged, but the private-vote-choice branch rewrites share_reveal in place to DOMAIN_VC_V2 vectors and deletes the V1 shares_hash code (VCB src/share_reveal/circuit.rs:1-33; diff stat: shares_hash.rs -741 lines). If V2 merges as is, DCs cannot be revealed and pooled weight is lost. Fix: V2 must keep the V1 scalar ZKP3 byte-identical as pool_share_reveal with its VK pinned to today's ZKP3, keep the V1 shares_hash/El Gamal gadgets (or ZKP4 vendors them), keep 0x04 as the scalar reveal tag, and give vector reveals a new tag.
- HIGH (privacy claims): owner decision 4 ('per-delegate totals stay hidden') cannot hold unconditionally. (a) Exact per-(proposal, option) totals plus public routes disclose Pool[d] exactly when d is the sole contributor to an option, and approximately by differencing turnout when d routes only some proposals. (b) Any coalition of at least t EA key holders can decrypt pools off-chain. (c) Per-delegate delegation counts are public, because each DC yields 16 reveals publicly tagged with d. Fix: state these precisely in ZIP-PD, the book and UI copy; recommend an Abstain option on every proposal and route-all nudges; never feed pool reveals into ShareCount; no count leaderboards. Keep ValidateEntryBounds rejecting proposal 0 as a tested invariant (keeper_voting.go:291-304).
- MEDIUM-HIGH (DoS and tree growth): '1 <= w <= W' lets a single VAN mint up to W fee-less DCs (W up to 2^30), each costing 16 helper ZKP3 proofs, reveal-cap slots near the deadline and a VCT leaf. AppendCommitment has no capacity check and an EndBlock error halts the chain (keeper_voting.go:99-117). Fix: in-circuit w >= min_dc_ballots as a ZKP4 public input bound to a round parameter (default 8 ballots), a per-block cap on proof-carrying vote actions, a tree-capacity guard returning ErrCommitmentTreeFull in DeliverTx, and a helper admission policy.
- MEDIUM (transaction size): a 'mixed ordered action list' with ZKP1 plus 10 DCs plus 50 casts is about 61 proofs of about 11 KB, roughly 680 KB of raw proof bytes. That exceeds the 1 MiB REST body limit (api/handler.go:780,814) after JSON/base64 encoding; the 50-cast delegate-and-cast is already about 78% of the cap. Fix: the chain advertises max_vote_tx_bytes and max_dc_actions_per_tx in ProtocolCapabilities, and the client splits into a DC batch plus a follow-up cast batch anchored on the final VAN.
- MEDIUM (observability and old-client hygiene): routing pool reveals through the existing reveal_share event or IncrementShareCount(round, 0, d) (msg_server_tally_decrypt.go:54-64) would expose a phantom 'proposal 0' to Zodl, old Vizor and explorers, and would skew VoteSummary. Fix: a distinct reveal_pool_share event and no ShareCount for proposal 0, with a regression test that TallyResults and VoteSummary never contain proposal 0.
- LOW (confirmation, not a flaw): 'Proposal-0 pools are excluded from decryption and completeness checks' already holds in code. Partial-decryption injection and completeness iterate round.Proposals (prepare_proposal_partial_decrypt.go:153-154; keeper_tally.go:307-341), and ValidateEntryBounds rejects proposal 0 entries (keeper_tally.go:408). The baseline only needs to add the routing hook in the TALLYING-transition EndBlock (module.go:491-512) before any partial decryption, plus tests that lock this in.
- LOW (operational): one-shot routes plus DK compromise means an attacker who routes first wins irrevocably for those proposals. Fix: document it, add a revocation path that blocks further routes, recommend seed-derived or enclave-held DKs, and let delegates route early. No protocol change for v1.

## open_questions_for_owner
- Minimum proxy-delegation amount per delegate (enforced in-circuit via a round parameter). Recommended: 1 ZEC (8 ballots), adjustable per round. 0.125 ZEC maximizes inclusion but amplifies helper-load and tree-growth DoS 8x.
- Per-delegate delegation counts are public on chain anyway (16 tagged reveals per DC). Should Vizor show them? Recommended: show the count only to the delegate in delegate mode, never rank or sort by it, and disclose publicly in docs that counts are public.
- Require an explicit 'Abstain' option on every proposal in proxy-enabled rounds? Recommended: yes. It lets delegates route every proposal, which limits pool-size inference by differencing, and makes delegate abstention visible instead of silent.
- Verifier trust at launch. Recommended: a single Valar verifier key (1-of-1) with the schema and chain threshold logic supporting t-of-n from day one, then a second independent verifier (for example Zodl or Shielded Labs) within two rounds.
- Ship the follow-mode v0 (directory plus signed voting guides plus copy-to-ballot) one round before B2? Recommended: yes, but only as a by-product of the B2 identity stack, and never if it delays the ZKP4 circuit work.
- May hardware-wallet-only users (Keystone/Ledger accounts with no seed in Vizor) act as delegates? Recommended: yes, with a random DK and a mandatory encrypted backup step. Seed accounts derive the DK via ZIP-32 registered derivation.
- Eligibility of delegates registered after a round is created. Recommended: they may receive delegations in that round, labeled 'new this round'; only delegates registered before round creation can be featured, and key rotations without the old DK take effect after cooling-off or at the next round.
- Default enablement. Recommended: proxy delegation is a per-round opt-in by the round creator; enable it for every public round after one successful mainnet round, keeping the Vizor remote kill switch.

## risks
- ZKP4 audit or circuit-fit slip (ZKP2 is at 98.4% of K=11) extends the critical path. A move to K=12 doubles prove time and key size.
- The V2 private-vote-choice PR merges without preserving the scalar ZKP3 and V1 gadgets, which breaks DC reveals and strands pooled weight.
- An accidental Zodl break from a config change (supported_versions, auth_version), event or field renames, or a proposal-0 leak into TallyResults or VoteSummary.
- Pool-size inference (sole-router and differencing) and public per-delegate counts are perceived as a privacy regression against owner decision 4.
- Verifiable vote markets: pools plus public routes plus no receipt-freeness make LobbyFi-style buying cheap; influencer concentration.
- DK compromise of a large delegate: one-shot routes are irrevocable, and the attacker who routes first wins.
- Helper or validator targeted censorship of reveals or routes for a specific delegate index (both are public and attributable).
- Helper capacity and the 256/block reveal cap at the end-of-round surge, worsened by dust DCs if min_dc_ballots is too low.
- EndBlock routing cost at scale (1,000 delegates x 50 proposals) and per-block ZKP4 verification cost without a cap.
- Transaction size: large mixed batches exceed REST and mempool limits unless the client splits them.
- X API pricing, policy or ToS changes and account-takeover or handle-recycling incidents. App-store UGC review of the delegate directory.
- Delegator device loss: Vizor hotkeys are unrecoverable, so the delegator loses the ability to verify (the weight is unaffected).
- A chain reset or genesis migration that does not carry the registry forward would reassign delegate indices.
- Snapshot equivocation by the directory operator or a CDN if wallets skip the per-round hash pin or chain cross-check.
- Mainnet [TEST] rounds signed into the prod config may be visible to Zodl users (the local Zodl checkout has no [TEST] filter).
