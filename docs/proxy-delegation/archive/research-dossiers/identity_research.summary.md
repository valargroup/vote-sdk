## design_implications
- Bind delegations and wallet favorites to a delegate identity public key (and X numeric user id), never to an @handle; handles are display-only and must be re-derived from the id at each refresh (NIP-05 rule; X recycles handles).
- Use a two-way binding: a public X post containing the identity key (X account vouches for key), plus an identity-key-signed registration statement containing the X numeric user id (key vouches for X account). This avoids the one-way impersonation of Cosmos 'identity' and Agora self-declared socials.
- Prefer a public-post proof over ICNS-style OAuth: it leaves a durable artifact anyone can re-verify, needs no token custody, deletion acts as a natural revocation, and the post itself advertises the delegate. Never forward OAuth tokens to multiple verifiers.
- Separate a long-lived identity key (bound once to X) from a per-round signed opt-in carrying the delegate's receive/hotkey address for that round. Hotkeys can then rotate without new posts, and inactive delegates drop out of new rounds automatically.
- Ship the registry as a signed, content-hashed static snapshot that wallets download whole and search locally. Reuse the existing zcash_voting Ed25519 trusted_keys and Vizor's sha256-pinned two-mirror loader, and pin the per-round registry hash in signed round config (needs a new RoundAuthPayload version or a separately signed document).
- Include raw evidence (post id, x_user_id, identity-key signature) in every entry so the key binding is client-verifiable and only the 'X says this account posted it' fact depends on verifier trust.
- Make verifier attestations threshold-capable from day one (list of {key_id, sig}, dedupe by signer key, no silent admin bypass), even if launch runs a single Valar/Vizor verifier. Today's trusted_keys semantics are 1-of-N.
- Use the official X API (about $0.005 per post read, $0.01 per user read) as the primary compliant source, oEmbed as a free fallback, and never the undocumented syndication endpoint in production. Budget about $30-$320 per month for 100-1,000 delegates.
- Design the proof post for 280 weighted chars, ASCII only, with no URLs or dotted tokens (t.co rewriting and auto-linking), and a fixed machine-parsable line such as 'zvote-delegate:v1:<bech32m key>'.
- Never let the wallet contact X or pbs.twimg.com. Pfps are fetched, re-encoded and content-addressed server-side, bundled with or referenced by hash from the signed snapshot, and optionally fetched over Vizor's Tor client.
- Keep X-derived content (pfp, display name, bio) in a mutable store refreshed at least daily, separate from any append-only or git history, to satisfy X's 24h deletion and update duties and delisting requests.
- Implement a lifecycle state machine: verified, then stale (transient errors, no change), then proof-removed (404, grace then delist from search), suspended/protected (flag), key-changed-pending (cooling-off unless co-signed by the old key). Freeze a per-round snapshot, allowing append-only additions mid-round.
- Support at least one non-X proof provider at launch (GitHub gist or domain DNS TXT/well-known), then Bluesky and Nostr, because X-only identity schemes (ICNS, Gitcoin X stamp) have been shut off.
- Search and discovery UX: exact-handle match first, confusable-skeleton lookalike warnings, key fingerprint or identicon, registration age, key-change history, a curated 'featured/endorsed' tier, follower and blue-check data as information only, and weighted-random default ordering to reduce influencer concentration.
- Delegation deeplinks (link.vizor.cash) must carry only an identity key or x_user_id and resolve the receive address via the signed registry, never an address shown next to a social label.

## risks_and_holes
- Handle recycling and resale: X frees deactivated handles after 30 days and its Handle Marketplace reassigns inactive handles. A registry keyed on handles would silently transfer an influencer's identity to a stranger.
- X account takeover: an attacker posts a new proof binding their own key. Without a cooling-off or old-key continuity rule, new delegations are redirected immediately. Existing delegations are safe only if they were bound to the key, not the handle.
- One-way bindings let anyone claim anyone: Cosmos validator identity field, Agora self-declared twitter. Must require the identity key to sign the x_user_id.
- OAuth token fan-out (ICNS): every verifier and the frontend held a live user token with offline.access. All 'independent' verifiers also depended on one X developer app, a single kill switch.
- Verifier threshold bugs: deduping by signature bytes instead of signer key (ICNS checks.rs L159-L170) and admin bypass of verification (contract.rs L121-L144) silently weaken t-of-n.
- No nonce or expiry in attestations (ICNS VerifyingMsg; ENSIP attestations have no expiry): stale attestations remain valid after account sale or takeover unless observed_at and freshness are enforced.
- X API breakage and ToS: free API ended Feb 2023; the syndication endpoint added a token in Aug 2023 and is undocumented; the ToS bans scraping; the Gitcoin X stamp was retired and ICNS registration is closed. Plan for X verification becoming unavailable.
- Transient X outages or rate limits causing mass de-listing if 5xx/429 are treated like 404. Need distinct failure classes and grace periods.
- oEmbed returns only the handle (author_url), not the numeric id. Using it alone after a rename can mis-attribute. Must reconcile with API-confirmed id mappings.
- Privacy leaks: hot-linked pfps reveal viewer IP and interest to X; per-query registry search reveals delegation intent to the server; per-delegate pfp fetches reveal the selection.
- Malicious image payloads targeting wallet decoders (libwebp CVE-2023-4863 used in BLASTPASS). Must re-encode server-side and pin by hash.
- Registry equivocation: an operator or CDN serves a targeted fake registry to one user. Mitigate with hash pinning in signed round config, multiple mirrors, and optionally an on-chain anchor.
- Compliance conflict: storing X content (pfps, names) in immutable git history violates X's keep-current and 24h-delete duties and makes delisting impossible.
- Dead or inactive delegates keep receiving delegations every round (Arbitrum: top-10 delegates hold 40%). Need a per-round opt-in and visible last-active or opt-in status.
- Influencer concentration and herding toward a few big accounts. Default ordering and featured lists shape the outcome; needs deliberate UX policy.
- Publicly identified delegates with large power make tally deltas informative. Their votes may be inferable (the submission-server ZIP already notes 'social context' closes linkage gaps).
- Delegate receive address not actually controlled by the delegate (typo or copy) strands delegated power; Orchard has no standard address-signature mechanism (ZIP 304 is Sapling-only draft).
- Lookalike handles (O/0, l/I/1, rn/m, extra underscores) and arbitrary Unicode display names. Pfp and display name are attacker-controlled and can be switched after verification.
- Sybil and spam registrations from cheap or bought-follower X accounts can flood search; follower counts and blue checks (paid Premium) are not trust signals.
- Edited posts and t.co rewriting can break naive parsers; protected accounts make proofs unreadable.
- Mid-round registry changes: freezing too hard blocks new delegates; changing live lets an attacker swap keys during voting. Needs an explicit append-only plus cooling-off rule.
- Deeplinks that embed an address alongside a social label can phish around the registry.
