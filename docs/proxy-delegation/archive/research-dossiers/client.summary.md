## key_facts
- Hotkey stored secret is 64 bytes and is used as a ZIP-32 seed: UnifiedSpendingKey::from_seed(network, secret, account 0), external address index 0 (zcash_voting/src/hotkey.rs:11-19, 41-105). Today's only generator is random OsRng (hotkey.rs:35-39), and docs say the secret is 'not wallet seed or mnemonic-derived material' (types.rs:510-515).
- zcash_voting already depends on zip32 0.2 (zcash_voting/Cargo.toml:82; Cargo.lock:4557-4558). zip32 0.2.1 provides registered::cryptovalue_from_subpath(context, seed, zip_number, subpath) -> [u8;64] (zip32-0.2.1/src/registered.rs:225-262), exactly the hotkey secret length. All voting ZIP drafts are 'ZIP: Unassigned' (zips/*.md:1-2).
- Local-hotkey VAN blinding is deterministic: BLAKE2b keyed by the hotkey secret, over network, round params, bundle_index and sorted note identities (van_blinding.rs:14-93). The public-target (custody) path samples random blinding that must be retained (delegate.rs:199-212; action.rs:494).
- One ZKP1 bundle holds at most 5 notes and produces exactly one VAN with num_ballots = floor(sum/12,500,000), minimum 1, maximum 2^30 (governance.rs:11-22, 85-110; voting-circuits delegation/README.md:339-356). The default bundle policy privacy-trims to at most 2 bundles (note_bundling.rs:21-52), so most wallets have 1-2 assignable weight units.
- TX1 is fixed at one Ironwood action. Its effects (821 bytes) include the output note's 580-byte enc_ciphertext and out_ciphertext and are published in MsgDelegateVote.tx1_effects (tx1.rs:16-27, 53-58; proto/svote/v1/tx.proto:57-69).
- The ZKP1 output is a zero-value note to the hotkey address with a 512-byte display memo stating the round and the raw zatoshi-precision bundle amount. OVK is set only for Ledger review (action.rs:163, 564-613; delegate.rs:2426-2463). The memo does not contain van_comm_rand.
- The chain stores only van_cmx in the tree and emits delegate_vote{round_id, leaf_index, nullifier count}. There is no REST endpoint listing delegation tx bodies, ciphertexts or cast actions per round (x/vote/keeper/msg_server.go:140-171; chain REST route list).
- ZKP2 condition 7 rebuilds the successor VAN from the same address, num_ballots, round and van_comm_rand; only proposal_authority changes (voting-circuits/src/vote_proof/circuit.rs:1104-1123; ZIP draft greg_shielded-voting-fixes.md:1364-1374 says the reuse is deliberate). Anyone holding the VAN opening can compute successor VANs.
- MsgCastVoteBatch appends only the final VAN to the tree and emits plaintext proposal_ids and final_van_leaf_index. Intermediate vote_authority_note_new values are only in the tx body (x/vote/keeper/msg_server.go:225-283). The SDK batches up to 50 actions (vote.rs:34).
- The van_integrity hash is pub(crate) in voting-circuits (src/gadgets/mod.rs:11). The client's plan_vote_authority_transition requires the hotkey seed (zkp2.rs:33-71). No public helper computes successor VANs from a public address.
- Tree sync downloads every leaf of the round, but leaves are bare commitments: it can verify or locate known VANs, not discover incoming ones (tree_sync.rs:441-559; vote-commitment-tree/src/client.rs:8-9, 320).
- VotingDb has no target or hotkey column. Bundles are keyed (round_id, wallet_id, bundle_index) with one gov_comm (VAN) each, and the target is re-validated against persisted cmx_new and gov_comm each step (001_init.sql:1-44; storage/operations.rs:151-230). Ballot intent is per (round, wallet, proposal), not per bundle (001_init.sql:170-181).
- DelegationPipeline and RoundExecutor each bind exactly one hotkey per round (delegation_pipeline/mod.rs:45-55; vote_work/mod.rs:45-57).
- Capability import requires a complete contiguous batch from index 0 and rejects partial, conflicting or pre-existing bundle state (delegation_capability.rs:379-457). Imported rounds block all new votes until every imported bundle is Confirmed (round_planning/classify.rs:212-221; docs/exporting-to-external-software.md:157-160). V1 is documented as one controller and one fresh hotkey per voter and round (doc:34-36).
- Capability export requires locally prepared and proven bundles for a single round-bound target and refuses rounds with combined delegate-and-cast (delegation_capability.rs:274-376, 283-290). Limits are 4,096 bundles and 1 MiB JSON (:27-37).
- chain_submissions.kind is CHECK-constrained to delegation/vote/vote_batch/delegate_and_cast_vote_batch, so a new submission kind needs a table rebuild migration (001_init.sql:201-245; migrations/006_delegate_cast.sql). Schema is at version 24, launch version 13 (storage/migrations.rs:5-25).
- Recovery after voting DB loss works only if the hotkey secret is restored: recoverable_bundle_policy_v1 plus deterministic blinding reproduce the VAN, and exact-tree recovery finds positions (CHANGELOG.md:265-272; note_bundling.rs:325-343; chain_submission/recovery.rs). recovery.rs itself is a read-only snapshot API.
- Vizor stores hotkeys per (accountUuid, roundId) in secure storage (vizor-wallet/lib/src/core/storage/voting_hotkey_store.dart). Vizor's participation check derives governance nullifiers from the FVK and verifies them via abci_query IAVL proofs (vizor-wallet/docs/voting-participation.md:9-31).
- Dynamic and static config wire structs do not use deny_unknown_fields (config/mod.rs:852-884), so optional new fields are backward compatible. Only round entries are signed (round_auth.rs:8-50), and every trusted_key authenticates rounds.
- Share limits: 16 shares per vote commitment, each < 2^30, greedy denominations up to 10M ballots (share_policy/server_order.rs:8; voting-circuits params.rs:16-23; vote_proof/builder.rs:39-128).
- Benchmarks: about 2 CPU-seconds per ZKP2 including overhead on Apple M4 Max (12 proofs, 23.5 CPU-s, 22.3 s wall at concurrency 1, peak RSS 180-330 MiB; docs/bundle_pipeline_benchmark.md:39-55). The book claims ~30 s register and ~15 s per vote ZKP (comparison-to-today.md:37-39). No mobile measurements exist in these repos. Prover workers use 64 MiB stacks (proving_runtime/mod.rs:16-31, 79).
- custody-voter is a Tauri desktop app: one random hotkey per (profile, round) in the OS Keychain, manual target JSON then capability JSON exchange, age-encrypted backups. It pins zcash_voting =3.0.0-rc.3 (custody-voter/README.md:63-90; docs/architecture.md:57-94; src-tauri/Cargo.toml:52).
- ZKP1 hardcodes MAX_PROPOSAL_AUTHORITY, so delegated VANs always carry full 50-proposal authority (voting-circuits delegation/circuit.rs:235-247; README section 7). The delegation circuit does not check ownership of the output address, so anyone can delegate to any address without the recipient's participation (README section 7).

## design_implications
- Percentage splits to up to 10 delegates need a circuit change. The cleanest client-side option is a post-delegation VAN-split proof signed by the delegator's own hotkey (no ZKP1, TX1, Keystone or Ledger change). The alternative is a multi-output ZKP1, which also changes TX1 framing, chain tx1 validation and hardware-signer review. Bundle-granular assignment (no circuit change) only works as a 1-2 delegate MVP.
- Delegate discovery can be on-chain through IVK trial decryption, because the ZKP1 output note is already encrypted to the hotkey address. That requires either a structured memo carrying num_ballots and van_comm_rand, or a protocol rule deriving van_comm_rand from the note's rseed, plus a new chain endpoint streaming per-round delegation ciphertexts with van_cmx and leaf_index. A VAN-split circuit needs its own per-output ciphertexts.
- Use the account OVK on proxy-delegation outputs so the delegator can recover delegate address and payload from chain data after reinstall. Combine this with blinding derived from delegator-owned recoverable material, not from the delegate's key.
- Delegate identity should be a seed-derived 64-byte secret via ZIP-32 registered key derivation (zip32::registered::cryptovalue_from_subpath, already a dependency) with an identity_index for rotation. Use a fixed address index 0 and a new round-free DelegateIdentityV1 format plus a public bind-to-round constructor. Hardware-wallet accounts need a random-key-plus-backup fallback.
- Keep incoming delegations in a dedicated VotingDb wallet_id scope per delegate identity. Add incremental, idempotent import keyed by van_cmx with allocated bundle indices, and replace the round-wide imported-capability confirmation barrier with per-bundle readiness.
- Add per-output target persistence (address, delegate identity reference, num_ballots, rand, VAN, tx hash, status) to VotingDb. The current schema has no target column and the host-owned target model does not survive reinstall.
- The round planner must classify proxy-delegated weight as 'delegated away': no cast obligation, separate status, separate kept versus delegated weight. Vizor's participation detector must distinguish 'delegated' from 'voted', since both spend governance nullifiers.
- 'Did my delegate vote?' can be built on successor-VAN computation. voting-circuits must export a public address-based successor-VAN or van_integrity helper, and the chain must expose cast-vote(-batch) events or tx bodies per round. Leaf-only sync is insufficient for batch casts.
- Any future VAN merge or split that re-randomizes VANs must deliberately preserve or replace delegator observability, for example with a public tag computable only from the delegator's known opening. Otherwise the 'did they vote' feature silently disappears.
- Plan delegate tooling for scale. Without a merge circuit, workload is incoming VANs × proposals ZKP2 proofs plus 16 helper shares each. Consider a minimum delegation size, a cap on VANs per delegator split, desktop or server delegate mode, and a workload estimator API.
- Use a structured, printable-ASCII memo for proxy delegations that shows the delegate's handle and the quantized ballot amount (not raw zatoshi), so Keystone and Ledger users can verify the recipient on-device and the delegate does not learn exact note sums.
- Add the delegate directory as an optional dynamic-config field (no deny_unknown_fields today), authenticated by a purpose-separated signing key or payload domain, not by existing trusted_keys (which authenticate rounds). Gate the feature via WalletCapabilities and supported_versions.

## risks_and_holes
- The ZIP rationale for reusing van_comm_rand across successor VANs assumes only the owner knows the VAN opening. With proxy delegation (and already with custody handoff), the delegator can trace the delegate's per-VAN proposal coverage and timing. This is a feature for accountability but a privacy change the spec must state.
- Batch casts append only the final VAN to the tree. A naive 'did they vote' check based on tree leaves will report false negatives unless it uses cast-vote-batch events (proposal_ids, final_van_leaf_index) or tx bodies.
- Today's delegation memo has no VAN opening, so a delegate cannot open received VANs from chain data alone. Shipping proxy delegation without a payload channel (memo, PRF rule or relay) strands the delegated weight.
- The current display memo reveals each bundle's exact raw zatoshi sum to the hotkey IVK holder (delegate.rs:2426-2449). For proxy delegation this leaks delegators' exact balances to influencers.
- Delegations are irrevocable within a round: governance nullifiers are spent at delegation. If the delegate never votes, the weight is wasted, and the delegator cannot override or reclaim it without a new circuit or Msg.
- Griefing: anyone can delegate to any address (no recipient consent in ZKP1). With splits, a holder could spray many 1-ballot VANs at an influencer and multiply the influencer's proof and helper workload. If the influencer ignores dust, delegators see 'not voted'.
- The imported-capability barrier blocks every vote until all imported bundles confirm. Reused for incoming proxy delegations, one stuck or rejected incoming delegation would block the delegate from voting with everyone else's weight.
- Capability import refuses any pre-existing bundle state, and ensure_bundles requires an exact persisted bundle count. Putting incoming delegations in the delegate's own voting scope would corrupt or refuse both flows.
- A seed-derived delegate key is long-lived: compromise exposes all incoming memos (IVK) and future delegated voting power. Rotation and directory revocation are needed. Hardware-wallet accounts (Keystone, Ledger) cannot derive it in Vizor at all.
- ZIP-32 registered derivation needs an assigned ZIP number. Using arbitrary derivation as a stopgap creates a key tree that must be supported forever for recovery.
- The delegator's DB loss without OVK-recoverable outputs or deterministic blinding loses the VAN openings. The delegator can then no longer verify the delegate's votes, and cannot even show which delegate received the weight.
- Delegate DB loss loses ballot intents and undelivered helper-share recovery JSON. VAN spend state must be rediscovered via VAN-nullifier queries or successor scans before re-voting, to avoid wasted work.
- A merge or consolidation circuit would create large, rare share denominations (1M or 10M ballots) that reveal whale-scale weight to holders of the full EA secret key, and would break delegator observability unless designed for it.
- A multi-output ZKP1 changes the chain's fixed 821-byte TX1 framing and the hardware-signer review flow (k recipients). It also reveals the delegate count per bundle on chain unless outputs are padded to a fixed number.
- No chain REST endpoint exists for per-round delegation ciphertexts or cast actions. Targeted lookups (fetching one tx by hash after a compact-decrypt match) leak interest to the server; full downloads cost bandwidth and depend on block or tx retention and pruning.
- A delegator splitting before voting gives delegates full authority. A delegator that votes on some proposals and then splits (VAN-split option) must carry the cleared authority bits, otherwise double counting is possible. The circuit must enforce sum and authority conservation, and the one-ballot under-claim window must not leak into split sums.
- The book's description of delegation (shielded-vote-book/delegation/*.md) omits how the delegate learns the VAN opening, says the delegate can 're-delegate' (which breaks the original delegator's tracking), and claims 'nobody can observe delegation amounts', which is false for the delegate and the delegator.

## open_questions
- Which split mechanism: bundle-granular MVP with no circuit change, multi-output ZKP1, or post-delegation VAN-split Msg and circuit? This decides whether Keystone, Ledger and TX1 framing change.
- Delegate discovery channel: on-chain memo payload (structured memo vs van_comm_rand derived from rseed), off-chain relay (for example vizor-deeplink-server), or both? Who operates the chain indexing endpoint, and what are the vote chain's block and tx retention guarantees?
- Should 'did my delegate vote' be a guaranteed product feature? If so, the protocol must commit to deterministic successor VANs (or a delegator-recognizable tag) and expose cast-batch events or tx bodies in a supported API.
- Is re-delegation by a delegate allowed (book says yes)? It breaks the original delegator's tracking and complicates authority accounting.
- Should a delegator be able to delegate only some proposals? ZKP1 currently hardcodes full proposal authority, so this needs a VAN-split design that carries a mask.
- Minimum delegation size and maximum outputs per split, to bound griefing and delegate workload; and whether delegates may ignore dust delegations (and how that is disclosed).
- Is a VAN merge circuit for delegates in scope? If so, how are EA-key-holder share-size leakage and delegator observability handled?
- Delegate identity derivation: obtain a ZIP number for registered key derivation now, or ship arbitrary-context derivation? What is the fallback for Keystone and Ledger accounts that have no seed in Vizor?
- Should delegate keys be stable across rounds (single published address) or rotate per round (directory publishes per-round targets)? What is the revocation and rotation story in the directory?
- Identity claim signature scheme for the X post: Schnorr proof of knowledge of ivk with base g_d and key pk_d (verifiable from the address alone) needs cryptographic review. Alternatively use a separate identity key registered in the directory.
- Where is the delegate directory declared and authenticated: a new optional dynamic-config field with a purpose-separated signing key, or the static config? Who runs the X-post verification oracle?
- Should proxy-delegation outputs always set the account OVK (enabling delegator recovery from chain data, and exposing delegate choice to anyone holding the account's viewing key)?
- Delegator recovery UX: is losing tracking after reinstall acceptable, or must delegations be fully reconstructible from seed plus chain data?
- Can an influencer's delegate role run on mobile Vizor, or only in a desktop or server mode, given incoming VANs × proposals ZKP2 proofs (no mobile benchmarks exist; about 2 CPU-s per ZKP2 on M4 Max)?
- Should delegators be able to see a delegate's aggregate delegated weight (a public leaderboard)? It is not computable publicly without delegate disclosure or a new ZK sum proof.
- custody-voter pins zcash_voting =3.0.0-rc.3 while Vizor pins 5.1.1-rc.3. Is custody-voter in scope for compatibility with a changed capability or proxy format?
