## key_facts
- VAN = Poseidon<2>(Poseidon<6>(DOMAIN_VAN=0, g_d_x, pk_d_x, num_ballots, voting_round_id, proposal_authority), van_comm_rand). The address is x-coordinates only, and the module warns the hash is not a standalone full-point commitment (voting-circuits/src/gadgets/van_integrity.rs:9-22,61-79).
- Proposal authority is 51 bits: MAX_PROPOSALS=50 plus a sentinel bit 0 that is always set and never decremented. ZKP1 bakes MAX_PROPOSAL_AUTHORITY=2^51-1 in as a circuit constant (src/params.rs:31-45; src/delegation/circuit.rs:1518-1525; src/vote_proof/circuit.rs:129-150).
- VAN nullifier = Poseidon<4>(vsk_nk, 'vote authority spend', voting_round_id, VAN). It is keyed by the VAN holder's nk, so only the hotkey owner can compute it (src/vote_proof/circuit.rs:206-230,1040-1070).
- ZKP2 binds a VAN to the hotkey through cond 2 (VAN preimage with witnessed address x-coords), cond 3 (CommitIvk(ExtractP([vsk]G), nk, rivk_v) and pk_d == [ivk]g_d), cond 4 (r_vpk = ak + [alpha]G, then an out-of-circuit signature) and cond 5 (nullifier with the same nk cell) (src/vote_proof/circuit.rs:894-967,1040-1070).
- ZKP1 already mints a VAN to an arbitrary recipient address. The output address is not checked against the delegator's ivk and is authenticated only through van_comm, rho_signed and the HW signature (src/delegation/builder.rs:716-728,843-861; src/delegation/circuit.rs:1225-1241).
- ZKP2's successor VAN reuses the same van_comm_rand, address, weight and round; only the mask changes (src/vote_proof/circuit.rs:884,1112-1131; src/vote_proof/builder.rs:423-461). vote_authority_note_new is public in every MsgCastVote, including batch intermediates (vote-sdk proto/svote/v1/tx.proto:76-113).
- Batch chaining is verifier-only. Each later ZKP2 in a MsgCastVoteBatch or MsgDelegateAndCastVoteBatch is verified against votetree.SingleLeafRoot(previous vote_authority_note_new or delegation van_cmx). Intermediate VANs are never appended to the tree, and the ZKP2 circuit is unchanged (vote-sdk x/vote/ante/validate.go:181-243,380-449; ffi/votetree/README.md:7).
- Measured on M3 Ultra (28 threads): ZKP1 is K=12, 4,039 of 4,096 rows (98.6%), 30 advice cols, 14 public inputs, 11,328 B proof, 116 ms prove, 2.34 ms verify, pk 156 MB. ZKP2 is K=11, 2,015 of 2,048 rows (98.4%), 34 advice cols, 11 public inputs, 11,008 B, about 71 ms prove, about 1.9 ms verify. ZKP3 is K=10, 976 of 1,024 rows, 13 advice cols, 9 public inputs, 4,992 B, about 26 ms prove.
- Measured unit costs: one Poseidon permutation is 37 rows, VAN integrity about 150 rows, a depth-24 vote-tree path about 912 rows, a variable-base mul 137 rows, a full fixed-base mul 85 rows, CommitIvk hash_to_point 52 rows. The README's '~1,560 rows' for the Merkle path is stale (src/vote_proof/README.md:136).
- The consensus proof-size cap is 15 KiB, 15,360 B (vote-sdk x/vote/types/keys.go:65-74; voting-circuits src/share_reveal/prove.rs:293). ZKP1 and ZKP2 proofs are within about 4 KB of it.
- All shared gadgets are pub(crate) (src/gadgets/mod.rs:6-12), so new circuits must be implemented inside voting-circuits.
- There is no in-circuit note encryption. However, MsgDelegateVote.tx1_effects carries the full 820-byte Ironwood action, including a 580-byte enc_ciphertext of the zero-value output note to the VAN address. The chain checks only that rk, nf and cmx match plus the sighash (vote-sdk proto tx.proto:57-69; ffi/tx1/effects.go:40-65; circuits/src/tx1.rs:26-35). The memo currently carries HW display text (zcash_voting/src/action.rs:566-609; delegate.rs:2422-2445).
- TX1 is fixed to exactly one action (ACTION_COUNT=1, vote-sdk circuits/src/tx1.rs:28-35), so a hardware wallet signs and shows exactly one output address and memo per delegation.
- Chain (voting-circuits =0.12.0) and clients (=0.12.2) have identical VKs. The diff touches only proving-preparation APIs and crypto deps, and the pinned VK fingerprints are identical; vk_fingerprint_unchanged passes on 0.12.2 (src/*/prove.rs:280/291/335).
- VKs are regenerated deterministically from Circuit::default() at process start, with no on-chain registry and no version field in the vote messages. protocol_hash.rs holds only Poseidon wrappers, not versioning (src/delegation/prove.rs:33-70; src/protocol_hash.rs:1-51; vote-sdk circuits/src/ffi.rs:609,819,996).
- voting-circuits has no stub, TODO or test for VAN split, merge or proxy re-delegation. The 'round_scoped_van_redelegation' tests cover cross-round reuse only (src/vote_proof/circuit.rs:2147-2208). The book's VAN split is an unimplemented 1-to-2 split with inherited mask (shielded-vote-book/delegation/partial-delegation.md).
- The hotkey is an Orchard SpendingKey from UnifiedSpendingKey::from_seed(64-byte secret, account 0), with the VAN target at fvk.address_at(0, External). Docs say to generate it once per identity and round. The ZKP2 builder hard-codes External scope and divides a zatoshi total by BALLOT_DIVISOR (zcash_voting/src/hotkey.rs:13-30,70-104; voting-circuits src/vote_proof/builder.rs:711-723,782).
- Local delegation derives van_comm_rand from the delegator's own hotkey secret plus round and notes (zcash_voting/src/van_blinding.rs:13-91), so the delegate cannot recompute it.

## design_implications
- Phase 0 needs no circuit change. Full proxy delegation already works by passing the delegate's published Orchard address as output_recipient to ZKP1. Partitioning notes into separate 5-note delegation bundles even gives coarse multi-delegate splitting at note granularity.
- Recipient discovery for ZKP1-minted proxy VANs can reuse the existing Orchard enc_ciphertext in tx1_effects at zero circuit cost: put (num_ballots, van_comm_rand) in the memo, or derive rand from the note rseed. The recipient verifies by recomputing the VAN against the public van_cmx, which makes garbage detectable.
- Answer to the user's question: yes. Today a delegator can learn every proposal (and the order and transactions) on which the delegated VAN was used, by recomputing successor VAN commitments, but not the decision. This only needs an exported, address-based transition helper in voting-circuits; there is no VK change.
- Prefer a new, additive VAN-split circuit that spends 1 VAN and outputs N VANs with inherited masks and weight conservation. It reuses ZKP2 conditions 1-5 and van_integrity, leaves ZKP1, ZKP2, ZKP3 and existing VANs untouched, and is plausibly K=11 with 3-4 Poseidon lanes for N up to 11 (K=12 fallback). Public inputs are 6+N.
- The split must use exactly ZKP2's nullifier derivation and the same per-round VAN nullifier set, must range-check every output weight, must keep DOMAIN_VAN and the round, and must sign a sighash that commits to the outputs and their ciphertexts with the hotkey key.
- Use the existing single-leaf-root batch pattern for an atomic 'delegate-and-split' (ZKP1 VAN to the delegator's own hotkey, then a split anchored at SingleLeafRoot(van_cmx)) and for 'split then vote with the retained output'. This keeps intermediate VANs out of the global tree and means the HW signs only the ZKP1 while the hotkey authorizes delegate selection, the same trust model as voting.
- Do not modify ZKP1 or ZKP2. Both are at about 98.5% of their row budgets, so any change bumps K (about 2x prove time and key size), changes the VK for every user, and for ZKP1 hits the single-action TX1 and HW display limit.
- For split-circuit recipient discovery, use out-of-circuit per-output ciphertexts (epk plus AEAD(weight and optional mask), about 64 B per output, with rand derived from the ECDH key and output index) and verify against the public output VAN commitments. In-circuit verifiable encryption costs about 300-360 ECC rows per output and threatens the 15 KiB proof cap for little benefit.
- If influencers will hold many received VANs, a merge circuit (M inputs owned by one key, about 1,140 Poseidon rows per input, K=12 for M of about 4-8) is likely needed to bound per-proposal ZKP2 and ZKP3 load. Use 'require equal masks' (cheapest) or AND; OR is unsound.
- Merge or re-split by the delegate breaks delegator tracking. Preserving it needs explicit public outputs: per-input consumption tags (about 40-75 rows), or provenance pads that let delegators recover the merged VAN's rand and weight (about 2 Poseidon calls per input, which leaks the merged weight to contributors).
- Per-output proposal subsets ('everything to A except proposal 3') are feasible as an extension: about 2k constraint terms for 51 bits x 11 outputs, with bit 0 excluded or forced to 1 and w_i <= w. A wide-gate layout adds many advice columns and may push the proof toward the 15 KiB cap. An interim workaround is to vote on the excluded proposal first and then split.
- VANs are round-scoped, so any VK change only needs to land between rounds and never needs migration of old VANs. The chain cannot run two VK versions in one round today.
- A delegate's long-lived published address is safe to reuse across rounds circuit-wise (VAN and nullifier include the round; the address never appears publicly), which supports stable ICNS-style identities. Zcash_voting currently assumes per-round hotkeys, though.
- Builder and API work needed in voting-circuits regardless: a ballot-denominated VAN API (builders currently take zatoshi), exported address-based van_integrity or transition helpers, and support for arbitrary recipient addresses and dummy outputs.

## risks_and_holes
- Double spend: if a split or merge circuit used a different nullifier tag or a separate nullifier set from ZKP2, one VAN could be both voted (producing a successor) and split. Weight would then be counted twice.
- Inflation through field wrap-around: a split without per-output range checks admits w_1 = w + k and w_2 = p - k. Output 1 is votable with inflated weight while output 2 is merely unvotable.
- Unsound merge masks: an OR (or 'max') of masks lets weight vote twice on a proposal one input already used. Only equal or AND masks are sound.
- Per-proposal conservation pitfall: if bit 0 is included, the rule degenerates into total-weight conservation. Outputs with no authority bits but unbounded weight must also be forbidden (w_i <= w).
- x-only address encoding: van_integrity_hash is not a full-point commitment. Any new design that keys encryption, ownership claims or identity binding off VAN x-coordinates alone is malleable to point negation (van_integrity.rs:14-22).
- Identical VAN commitments, for example a reused rand or ECDH key for the same recipient, weight and mask, produce identical nullifiers, so all but one become unspendable. Derivations must include the output index and a fresh epk.
- Garbage or missing ciphertexts can only be detected, not prevented. Wallet UI must count only VANs whose opening re-hashes to the public commitment; otherwise phantom 'received' weight is shown.
- Delegate scaling: without a merge, an influencer with N delegators must produce N ZKP2 proofs and 16N ZKP3 reveals per proposal. That is about 70 ms per proof on desktop and much more on mobile, plus chain and helper load. Weight-1 dust delegations amplify this, so a minimum weight or dust policy is needed.
- Delegate tracking is inherent today: delegators (and anyone they share the VAN opening with) see which proposals the delegate voted on with their weight. A merge or re-split circuit lets delegates silently evade this unless tags are designed in.
- The delegate always learns the delegator's exact ballot weight, which for a full note-bundle delegation is the delegator's balance rounded down to 0.125 ZEC. The book's claim that amounts are unobservable is wrong for the delegate.
- Vote-selling becomes trivial and verifiable: delegation transfers voting power directly, and the delegator can confirm usage on-chain. The system is already not receipt-free, since a voter can reveal (shares_hash, decision) for their own vote commitment.
- Hardware-wallet verification of who receives voting power is weak. Addresses are opaque, the memo is written by the host wallet, and TX1 shows a single output. Multi-VAN ZKP1 would hide additional delegates entirely, so the host wallet is trusted for delegate selection.
- Modifying ZKP1 or ZKP2 pushes K up by one: ZKP1 has 57 rows of headroom and ZKP2 has 33. That roughly doubles prove time and pk size (156 MB to about 300 MB for ZKP1) and forces a chain-plus-client VK upgrade for all users.
- The 15 KiB consensus proof cap (keys.go:65-74) can be exceeded by wide new circuits, for example a per-output-mask chip with about 37 advice columns or extra ECC lanes for verifiable encryption.
- A recipient address the delegate cannot actually open burns the weight silently: a wrong address index or scope, a typo, or an address from a different key. The ZKP2 builder only proves for fvk.address_at(index, External). Hotkey docs assume per-round hotkeys, while ICNS-style identities need stable addresses.
- Unrestricted re-delegation: a split circuit cannot tell received VANs from the holder's own VANs, so transitive delegation is automatically possible unless the VAN format adds a flag. A flag moves the ZKP1 and ZKP2 VKs.
- Tree growth: a fixed-arity split appends N leaves, dummies included. Capacity is 2^24 leaves per round (params.rs:47-56), which is fine but should be budgeted.
- Delegation is irrevocable within a round, and the delegator cannot override the delegate per proposal (there is no Cosmos-style override) unless authority is reserved via per-output masks before handing off.
- The concurrent ZKP 1.5 private-choice redesign (docs/design.md) also changes the ZKP2 and ZKP3 VKs and DOMAIN_VC. Uncoordinated rollouts would require two VK bumps.
- Stale or inconsistent docs could mislead implementers: the Merkle-path row count in the vote_proof README, 15 vs 14 conditions for delegation (README.md:111 vs circuit.rs:3), and the book's amount-privacy claim.

## open_questions
- Is it acceptable, or even desirable as accountability, that delegators can see which proposals a delegate used their weight on? If not, ZKP2 would need to re-randomize the successor rand, which is a VK change and also removes the 'did they vote' feature.
- Should transitive re-delegation (a delegate splitting received VANs onward) be allowed, or does the VAN format need a non-delegatable flag (a ZKP1 and ZKP2 VK change)?
- What is the expected maximum number of delegators per influencer? This decides whether a merge circuit is required in v1, and which mask policy to use (require equal vs AND).
- Are per-proposal exclusions ('delegate everything except proposal 3') required in v1, or is 'vote on 3 first, then delegate the rest' acceptable?
- Fixed-arity N-output split with dummy outputs (hides the delegate count, appends N leaves, one proof) vs repeated 1-to-2 splits batch-chained (smaller circuit, leaks the count)? Should N be 11 (10 delegates plus change)?
- Is a minimum delegated weight or dust policy needed to protect influencers from forced proof work?
- Do delegators need revocation or a Cosmos-style per-proposal override? Neither exists, and either needs a new spend path.
- Recipient-discovery encoding: reuse the ZKP1 output-note memo (which is currently HW display text) or a new compact per-output ciphertext field? Does the chain persist and serve tx1_effects for delegate scanning? I could not verify this here.
- Does Keystone or Ledger render zero-value outputs and memos? The README states only that zero-value spends are not rendered. This is unverified, and it matters for any multi-output ZKP1 design.
- Should the ICNS registry require a cryptographic proof that the X-linked address is controllable by the poster? That would need a new small address-ownership-attestation circuit (about 400-500 rows), versus trusting the X post alone.
- Should influencers keep a long-lived voting hotkey across rounds, which is safe circuit-wise, or publish a new address each round? Current zcash_voting docs assume per-round hotkeys.
- Is the delegate learning each delegator's exact weight acceptable, and how will the UX disclose it?
- Upgrade plan: ship the new circuit at a round boundary with a chain upgrade, and decide whether to bundle it with the ZKP 1.5 / DOMAIN_VC_V2 VK changes.
- Not measured: mobile prove times. The desktop M3 Ultra figures (ZKP1 116 ms, ZKP2 about 71 ms, ZKP3 about 26 ms) need device benchmarks for Vizor.
