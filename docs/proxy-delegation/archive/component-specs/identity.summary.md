## key_decisions
- **Each delegate has two Ed25519 keys: a DIK (identity) and a DRK (route). Both are app-level software keys, independent of wallet accounts and funds.** — A leaked hot route key can be rotated immediately by the DIK. The delegate keeps its index, its X proof and its delegators' favorites. The DIK can be kept cold. Delegates need no ZEC or VAN in B2, so hardware-account users can be delegates. Ed25519 verifies cheaply in Go stdlib with no cgo, zcash_voting already links ed25519-dalek, and the tooling is universal. (rejected: Single DK: theft allows an instant co-signed rotation and owner lockout. RedPallas DK: needs a cgo FFI call on every route, and no circuit benefits. secp256k1/ADR-036: ties identity to coordinator-created Cosmos accounts. Orchard-address keys: proving control needs a ZK construction.)
- **Every DIK change is delayed: 72 h when co-signed, 7 days for verifier-attested recovery. Either current key can cancel it. DRK rotation by the DIK is immediate. Revocation by the DIK is immediate and terminal. Freeze can be done by the DIK or the DRK.** — Revocation is monotonic, so whoever holds the current DIK can always end the entry before a hostile identity change lands. A stolen key's worst case is routing the current round's un-routed proposals, which equals the DRK-theft case. X account takeovers get a 7-day public window. (rejected: Immediate co-signed DIK rotation (an attacker locks the owner out). Delayed DRK rotation (the owner cannot stop a leaked hot key in time). Letting the DRK revoke (a stolen hot key could destroy the index; freeze gives the panic button without permanent damage).)
- **The on-chain registry stores only the index, DIK, DRK, key_epoch, status, coordinator suspension, provider code, a SALTED subject_commit, the pending change and heights. Handles, ids, post ids and pfps stay off chain.** — Tx bytes and state are retained forever, so anything in an attestation is permanent. Deleting the salt from the mutable store makes the on-chain commitment unlinkable, which satisfies the X 24 h deletion duty. Wallets recompute the commit from the snapshot's (id, salt), so the id-to-key binding is still checked against consensus. (rejected: Plain or unsalted x_user_id hash on chain: allows chain-level uniqueness but is permanent X-derived data. Verifier-HMAC tag: needs a secret shared across independent verifiers.)
- **Signatures are always over fixed-width BLAKE2b-256 digests with ASCII domain prefixes (the chain sighash convention). JSON is only transport and evidence.** — Go (chain), Rust (wallet, verifier) and Dart never need to agree on JSON canonicalization. The digest layouts mirror existing sighash.go conventions, and shared test vectors are easy. (rejected: RFC 8785 JCS-signed JSON statements, which risk cross-language canonicalization bugs in a consensus-adjacent path.)
- **Two-step proof flow (resolve, then attest) with a brand-neutral marker line 'zcash-vote-delegate v1 zvdk1...'. GitHub gist and DNS TXT / well-known variants use the same marker. Binding is by numeric account id.** — The client cannot learn its numeric X id from a URL, but the DIK must sign the id (two-way binding). The marker has no URL, dots or symbols, so X does not auto-link it, and it is 137 characters with the suggested first line. Numeric ids defeat handle recycling and the X Handle Marketplace. (rejected: OAuth token flow (ICNS bearer-token fan-out, no public re-checkable artifact). Keying on handles. Including signatures in the post (too long; adds nothing).)
- **Threshold attestations go on chain: a coordinator-managed verifier set with separate register and recover thresholds. Every signature must be from a current verifier and valid. Signers are deduplicated by verifier_id, and set validation enforces unique pubkeys. Attestation ids are client-random, single-use, with expiry of at most 72 h. There is no admin bypass; the only coordinator power over an entry is suspension.** — This fixes the ICNS flaws: signature-byte dedupe, admin bypass, and no nonce or expiry. It keeps registration fee-less but spam-gated by verifier issuance policy, and allows t-of-n independent verifiers later without changing the chain. (rejected: Verifier-submitted standard Cosmos txs from verifier accounts (the chain cannot then check PoP in one place, and the verifier must be a chain participant). Coordinator approval per registration (too much friction for open listing).)
- **Pending identity changes take effect lazily (effective view computed at read time) rather than in EndBlock.** — EndBlock errors halt the chain. Lazy evaluation is deterministic, needs no per-block work, and route verification always uses the effective keys. (rejected: EndBlock activation queue (halt risk and per-block iteration).)
- **Directory is split into: chain registry (authoritative keys and status), a public ID-only registry doc, an X-hydrated profiles doc with a 30 h expiry, and content-addressed avatars. All are signed by a purpose-separated directory key in a new optional static-config section, with an offline key for certs and revocations. Snapshots are hash-chained with monotonic seq and dual-mirror equivocation checks.** — Separates consensus facts from mutable X content (keep-current and 24 h deletion). Lets other wallets consume ID-level bindings without redistributing hydrated X objects. Old wallets and Zodl ignore the new optional field. (rejected: Pinning a per-round directory hash in the signed RoundEntry (a new auth_version makes old wallets skip rounds, and frozen X content conflicts with the deletion duty). Signing with round trusted_keys (breaks purpose separation). GitHub Pages hosting (immutable history of X content).)
- **Profile pictures are fetched and decoded server-side only, with pure-Rust decoders in a no-network sandbox. They are re-encoded to WebP at 64 and 256 px, hash-pinned in the signed profiles doc, and served from our origin in packs. Clients decode in Rust and hand raw pixels to Flutter.** — Untrusted images are a zero-click exploit vector (CVE-2023-4863 / BLASTPASS). This design puts a signing-key compromise plus a memory-safe-decoder bug in front of any wallet parsing attacker-influenced bytes. Wallets never contact X, and Tor-friendly bulk fetches avoid per-delegate leaks. (rejected: Hot-linking pbs.twimg.com (privacy leak, ToS fragility, platform-codec exposure). Image.network (bypasses Tor policy). PNG output (3-4x larger).)
- **Delegate keys are derived from a dedicated 24-word delegate key phrase with keyed BLAKE2b (identity and route generations). They are not derived from the wallet seed in v1.** — Works for hardware-wallet accounts (no seed in Vizor), needs no ZIP number for ZIP-32 registered derivation, separates the public persona from funds, and enables a dedicated delegate device. Restore scans generations against the chain registry. (rejected: ZIP-32 registered derivation from the account seed (blocked on a ZIP number and unavailable for hardware accounts). Random keys with file backups (worse recovery UX).)
- **Hosting is on valargroup infrastructure (DigitalOcean, alongside the vote chain and config pins), with functions.vizor.cash as an untrusted mirror. X API is pay-per-use as primary, oEmbed only for re-verifying existing entries, and the syndication endpoint is never used.** — The verifier is cross-wallet protocol infrastructure with keys registered on the vote chain. The deeplink server is stateless by charter. Official API plus oEmbed are published interfaces under the X ToS. (rejected: Hosting in Vizor's lambda as primary. Syndication or third-party mirrors (ToS and trust problems).)
- **Search is entirely local: exact handle, key or fingerprint matches first, then featured, then listed, in daily-seeded weighted-random order. Follower counts and pool sizes are never used to sort or shown. Listing thresholds gate browse visibility only; exact lookup always works.** — Avoids server-side query logs of delegation intent and concentration feedback loops (Arbitrum's top-10 delegates hold 40%). Cheap X accounts can register but cannot crowd the browse list. (rejected: Server-side search API (leaks intent). Popularity sort.)

## baseline_challenges
- MEDIUM: a single long-lived DK for the X proof, registry and routes is unsafe. Theft allows an immediate co-signed rotation that locks the owner out of the index permanently. Fix: split into DIK (identity, cold) and DRK (route, hot). DRK rotation by DIK is immediate; every DIK change is delayed (72 h co-signed, 7 d attested recovery) and cancellable by either current key; revoke by DIK is immediate and terminal.
- MEDIUM: the baseline's 'per-round pinning' of a hash-pinned profile snapshot cannot sit in the signed round config. verify_round_entry returns false for any auth_version other than 2 (zcash_voting config/mod.rs:1098-1101), so old Vizor and Zodl would skip the round. A frozen per-round copy of X content also conflicts with X's 24 h deletion and keep-current duties. Fix: make the on-chain registry the per-round consistency anchor. Add hash-chained monotonic snapshots with dual-mirror equivocation checks, wallet-side pinning of each delegation (index, DIK, fingerprint, handle, directory seq), and an optional daily on-chain directory anchor in Phase 2.
- MEDIUM: the DC hides delegate_index until the share reveal, so the chain cannot refuse a proxy delegation to a revoked, frozen or suspended delegate. That weight silently abstains. Fix: (a) the wallet re-reads the chain registry overlay immediately before signing and blocks non-ACTIVE, suspended or pending-change delegates; (b) a RevealShare with proposal_id 0 accepts any decision in [1, next_index) regardless of status, so share accounting stays consistent; (c) the UX discloses that un-routed pool weight abstains.
- LOW-MEDIUM: 'bio' in the profile snapshot is X content that adds compliance load. Fix: drop the X bio. Use a DIK-signed, delegate-authored statement of at most 500 chars, which also gives delegates a platform not tied to X.
- LOW-MEDIUM: a plain x_user_id commitment on chain is permanent X-derived data, because tx bytes are retained forever. Fix: store a per-registration SALTED subject_commit. The salt lives in the mutable store and is shredded on deletion. Uniqueness is enforced by verifier policy plus public audit, not consensus.
- LOW: fee-less custom-wire registry operations need explicit spam bounds beyond attestations. Fix: max_registry_ops_per_block, enforced in PrepareProposal and ProcessProposal like the 256 reveal cap; a lifetime cap of 64 key changes per delegate; keys never reused; registration gated by a threshold attestation.
- LOW: if the directory signing key lives only in the hash-pinned static config, rotating it after compromise needs an app release. Fix: list an online key plus an offline key; the offline key signs key certificates and revocations that wallets honor.
- LOW: user-facing 'delegation' wording collides. Vizor today calls ZKP1 'voting delegation' in the UI. Fix: rename that copy to 'voting authorization' so 'delegate' means only a person.
- INFO (outside my component, flag for integrator): with 16 share reveals per DC under proposal 0 / decision = delegate_index, the public ShareCount per (round, 0, d) reveals each delegate's number of incoming proxy delegations (about count/16). That is not a total, but it is a public popularity counter that decision 4 does not cover.

## open_questions_for_owner
- Should network coordinators have an on-chain 'suspend delegate' power (freeze-only, threshold action, public reason code) as the backstop for confirmed impersonation or verifier compromise? Recommended: yes, threshold of at least 2, freeze-only, every use shown in wallets. It can never create entries, change keys or re-route weight.
- Listing thresholds for browse and partial search. Recommended: X account at least 180 days old with at least 100 followers and registered at least 24 h, or featured. The registration gate is 30 days. Exact handle, fingerprint and deeplink lookup always works.
- Delegate keys from a separate 24-word delegate key phrase, or from the wallet seed? Recommended: separate phrase for v1 (works for Keystone and Ledger users, no ZIP-number dependency). Revisit seed derivation once a ZIP number is assigned.
- Initial verifier trust. Recommended: launch 1-of-1 (Valar) for registration, with recover_threshold raised to 2 as soon as a second key exists. Move to 2-of-3 with at least one independent organization within 6 months.
- X API budget at scale (about $3.4k per month at 10k hydrated delegates). Recommended: approve de-hydrating dormant delegates (no route in 3 rounds, not featured, registered at least 90 days). That brings 10k delegates to about $1k per month. Dormant entries stay registered and resolvable by fingerprint until the delegate refreshes.
- May other wallets consume the X-hydrated profiles document, or only the ID-level registry document? Recommended: publish the registry doc openly. Treat the profiles doc as display data for Vizor until counsel reviews the X Developer Agreement redistribution clause and the ToS effective 2026-10-09.
- Should follower counts be shown to delegators? Recommended: no. Show account age and recent routing activity instead, to avoid popularity concentration.
- Featured tier size and composition. Recommended: at most 30 featured, a 2-of-3 curator approval rule across Valar and Vizor, and a public featured log with reason codes.
- Identity-change delays. Recommended: 72 h for co-signed DIK rotation and 7 days for attested recovery, both coordinator-adjustable.

## risks
- Verifier compromise. A compromised verifier threshold can register impostor entries and start identity recoveries on any delegate. Recoveries are visible and cancellable for 7 days, but an inattentive owner could lose the entry. Mitigations: recover_threshold of at least 2 once multiple verifiers exist; signer rate caps; issuance-to-chain reconciliation alarms; manual review for featured delegates.
- Directory key compromise allows presentation-layer lies, for example labeling an attacker's subject id with a victim's handle. Chain checks do not catch this because the subject_commit matches the attacker's real id. Detection relies on monitors, equivocation checks and the Phase 2 on-chain anchors.
- X platform dependency: API price changes, app suspension, ToS changes (new ToS effective 2026-10-09) or a Gitcoin/ICNS-style shutdown of X-based verification. On-chain keys survive, but discovery degrades. Shipping GitHub and DNS providers at launch is the hedge.
- X Developer Policy compliance for public redistribution of hydrated profiles across wallets is unresolved and needs legal review. The 24 h deletion duty depends on daily refresh plus CDN purges working reliably.
- Weight stranded by status changes. Delegators who delegated to a delegate that is later frozen, suspended or revoked see un-routed proposals abstain. The chain cannot block such delegations at DC time because the index is hidden until reveal.
- Route-key theft causes irreversible damage in the current round, because routes are final and one-shot. Key separation limits only future rounds. The delegate UX must push phrase backup and device hygiene, and offer a quick pause.
- The X oEmbed fallback carries no numeric id. A handle-reassignment race during an API outage could be misread. It is mitigated by accepting oEmbed only when the handle matches the last API-confirmed handle within 7 days, and never for new registrations.
- Lookalike detection is heuristic (UTS #39 skeletons, edit distance, pHash). Determined impersonators with distinct-looking handles that trade on display names or bios can still mislead users. Fingerprint display and the featured tier are the backstop.
- Cloud KMS Ed25519 availability is unverified for some providers, and YubiHSM on DigitalOcean is not possible (no USB). Key custody may force a small dedicated host or a different cloud for the signer.
- Fee-less registry operations still let a registered delegate churn state. This is bounded by the per-block cap and the 64 lifetime key-change cap, but genesis and state growth should be monitored.
- Per-delegate delegation counts become public via proposal-0 ShareCount (about shares/16). That is a popularity counter and a coercion signal not covered by the 'hidden totals' decision. Flagged for the integrator.
- Cross-language digest mismatches between Go (chain), Rust (wallet, verifier) and any CLI would break registrations. A shared test-vector fixture is mandatory in CI on both sides.
