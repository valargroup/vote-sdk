## key_decisions
- **Extend the existing VotingSubmissionJobNotifier with a proxy mode instead of adding a second job.** — The two jobs would share the same (account, round) session key, VotingSubmissionGuard, serialized SDK session (_enqueue), Keystone/Ledger panels and status screen. The SDK composes ZKP1 + DCs + casts into one atomic batch per VAN, so one driver over the SDK plan is the natural shape. Adds VotingSubmissionKind {ballot, proxy, proxyAndBallot}, ProxyJobStage and terminalReason. (rejected: A separate VotingProxyDelegationJobNotifier, which would duplicate about 1,000 lines of hardware-signing branches and race the vote job on the same SDK round; a client-side orchestrator that builds DCs in Dart (the README forbids Dart mirrors of durable rows).)
- **The SDK owns allocation rounding and VAN packing. Dart calls a pure preview FFI on each edit and only formats the result.** — One source of truth for ballots (0.125 ZEC), the at-least-1-ballot rule, at most 10 DCs per VAN and first-fit-decreasing packing across up to 2 bundles. The preview and the recorded plan cannot disagree. (rejected: Dart-side rounding mirrored in Rust (drift risk); exposing VAN or bundle structure to users (confusing, and a privacy-trim detail).)
- **Delegation is offered per round only while no own cast has been submitted (SDK proxyAvailability). Users can 'Delegate more' before voting, and a combined review submits delegations and their own votes atomically.** — Vizor casts on all bundles together and ballot intents are per round, so a round-level rule is the one users can understand. The SDK still enforces the per-VAN MAX-authority rule. The combined path gives one tx per VAN, best for privacy and fewest steps. (rejected: Per-VAN availability in the UI (confusing after partial submissions); delegate-only flows with no combined submit (more txs and timing links).)
- **The delegate role is limited to software accounts in v1. The DK is derived on demand in Rust from the account seed (zip32 arbitrary context, identity_index for rotation) and never stored.** — Seed restore recovers the delegate identity with no extra backup. The secret never leaves Rust. The DK is a hot key in either case, so a hardware account adds no protection. (rejected: A random DK with its own backup phrase for hardware accounts (more UX and a recovery burden; deferred); reusing per-round voting hotkeys (not publishable, not recoverable).)
- **Registry discovery is a signed whole-snapshot download with local search, content-addressed thumbnails or a thumbnail pack from a Vizor/Valar origin, Image.memory only, and no contact with X.** — No per-query interest leak, Tor-compatible, keeps the existing no-remote-image posture, re-encoded images shrink decoder attack surface, and it supports X's 24-hour deletion duty server-side. (rejected: Server-side search API (logs intent); hot-linking pbs.twimg.com or Image.network (bypasses Tor, leaks IP); per-profile image fetch only (leaks which profiles a user viewed).)
- **Verify delegate routes, delegate chain records and DC share nullifiers against the chain's signed header with the existing IAVL participation reader. Fetch routes as whole-round incremental lists, with decoy keys in verification batches.** — Gives delegators end-to-end verifiability without trusting REST, and reuses audited code. Routes are one-shot, so a proved route can be cached forever. (rejected: Trusting REST responses (no verifiability); per-delegate route queries (reveal the user's delegate choice to the RPC, correlatable with the proxy tx IP).)
- **Deep links carry only the delegate_index plus an optional key-fingerprint hint in the fragment (link.vizor.cash/d/123#k=...). The server page is generic and has no per-delegate data.** — Keeps the gateway stateless (no database, no remote assets). The index is the chain identity the pool follows. The hint detects key changes since the link was made. No spoofable per-delegate OG card. (rejected: Handle in the path (handles are recycled and resold); server-rendered per-delegate cards (breaks the stateless charter and helps phishing); a wildcard route.)
- **Gating fails closed and requires all of: build define, remote flag, WalletCapabilities, signed config capability, chain ProtocolCapabilities with a matching ZKP4 VK fingerprint, and a valid registry. The beta runs on [TEST] rounds. Status views are never hidden once the user has delegated.** — There is no on-chain VK registry and no per-round circuit version, so a VK mismatch must be caught before proving. Old clients stay untouched because vote_protocol is not bumped. (rejected: Config-only gating (VK skew would cause rejected txs after broadcast attempts); bumping vote_protocol (breaks Zodl and old Vizor).)
- **Finality is acknowledged with an explicit checkbox and the CTA amount ('Delegate 37.5 ZEC'). Cancel is allowed only before the first broadcast, and NOT_SENT plans can be resumed or discarded.** — The owner decided delegation is final per round. The point of no return must be visible and must line up with the SDK broadcast state. (rejected: An undo window (impossible after broadcast); hold-to-confirm gestures (accessibility cost).)
- **User-facing naming: 'authorize voting' for ZKP1 (rename the Ledger 'Preparing voting delegation' copy), 'delegate/delegation' only for proxy delegation, and 'public vote' for MsgDelegateRoute. Code uses the proxy*/Delegate* prefixes.** — Removes an existing user-visible collision and keeps code and spec terms distinct. (rejected: 'Proxy voting' as the user term (unfamiliar); keeping the Ledger 'delegation' copy (ambiguous next to the new feature).)
- **A public vote by a delegate requires wallet re-auth (password or biometrics) and a confirm sheet whose button names the choice. The route is one-shot and final.** — One DK signature permanently routes a potentially large pool, and the key is a hot key on the phone. (rejected: Single-tap voting (high misclick and theft impact).)
- **New delegation is allowed until vote_end_time minus 10 minutes, with a warning in the last 24 hours that shows each chosen delegate's progress.** — Parity with own votes. Late delegation to a delegate who has already voted is informed delegation and is useful. (rejected: An early client-side cutoff with no chain basis (blocks legitimate use).)

## baseline_challenges
- [High] Proposal_id 0 crosses many validated boundaries besides the unchanged ZKP3 circuit. Chain RevealShare ValidateBasic requires proposal 1..50 and decision < 8. Helper ingest validates the same ranges. The SDK has validate_proposal_id plus the VotingDb CHECK proposal_id BETWEEN 1 AND 50. The votes UNIQUE(round, wallet, bundle, proposal) and share_delegations (bundle, proposal, share) keys collide when one VAN carries several DCs that all use proposal 0. Vizor UI keys (VotingVoteKey, voting_resume_plan.dart:29-49) assume real proposals. Fix: DC shares get their own SDK tables keyed (bundle, dc_index, share_index) and their own NextStepKinds (proxyDelegate, advanceProxyDelegation, submitProxyShares, confirmProxyShare). The chain and helpers accept (proposal 0, decision = any assigned delegate_index < 2^32). Vizor never surfaces proposal 0.
- [High] Mixed-batch size. The chain dossier estimates a 50-vote delegate-and-cast at about 78% of the effective REST/Comet JSON cap (about 750 KB raw). Adding up to 10 DCs (ZKP4 proof about 11 KB plus 16 ciphertexts each) on top of 50 casts can exceed it. Fix: the SDK splits a VAN's ordered action list into several txs when over budget (ZKP1+DCs first, then casts), and the chain advertises max_vote_tx_bytes in ProtocolCapabilities. The UX stays the same because the job reports tx i of n.
- [Medium] Count oracle. Reveals publish (proposal 0, decision = delegate_index), so the number of DCs per delegate (about reveals/16, less exact in last-moment single-share mode) is public, even though per-delegate totals stay hidden. Copy must not promise that delegation counts are private (C4b). The owner should decide whether Vizor shows the estimate anywhere (recommended: only on the delegate's own dashboard).
- [Medium] Pool follows delegate_index, not the key. A DK rotation during an ACTIVE round silently redirects every existing delegator's pooled weight to whoever controls the new key, for example after an X account takeover. Fix: rotations not co-signed by the old DK must not take effect for routing until the round ends (cooling-off covers vote_end_time). Every rotation is exposed via key_history so Vizor can show 'Key changed' to existing delegators, and Vizor checks each route's signer key against the key valid at that height.
- [Medium] The DC hides delegate_index, so the chain cannot reject delegations to inactive, revoked or nonexistent delegates at submission time. Reveals for any assigned index must always be accepted (rejecting at reveal would destroy the delegator's weight rather than abstain). Inactive delegates should still be able to route in rounds already in progress. Vizor must block new delegations to non-active entries client-side, using the proved chain record at review.
- [Medium] Proxy-only rounds need a durable 'proxy intent' in the SDK planner. Today the planner schedules ZKP1 only for bundles with ballot intents (voting_submission_job_provider.dart:669-680), so a Keystone/Ledger user who only delegates would never be asked to sign, and _run fails with 'Choose at least one vote before submitting.' (:664). Fix: set_proxy_allocation is a first-class durable intent that makes ZKP1 (and its signing need) plannable without votes.
- [Medium] Delegator recovery. DC openings and share nullifiers derive from the random, unrecoverable per-round hotkey, so after reinstall or seed restore the delegator cannot see which delegates they chose or verify reveals, although the delegation still counts. This weakens the 'end-to-end verifiability' goal across reinstalls. Options: accept and disclose (recommended for v1), or add an OVK-keyed recovery receipt (delegate_index, ballots) per proxy batch so the seed can recover the choices (a protocol and state change).
- [Low] Existing user-facing copy already calls ZKP1 a 'delegation' (Ledger 'Preparing voting delegation' / 'Finishing voting delegation', voting_status_screen.dart:1262-1263). Rename it to 'authorization' before launch to avoid ambiguity.
- [Low] Registry snapshot vs chain divergence. Profiles (handle, photo) are off-chain while keys and status are on-chain. The snapshot must carry dk_pubkey, status and attestation_hash so the wallet can cross-check against an IAVL-proved chain record. The chain must store registry entries and routes under documented deterministic KV keys (not events only) so membership and non-membership are provable.
- [Low] Round-level feature flags in the dynamic config are not covered by RoundAuthPayloadV2 (round_id || ea_pk || pir layout). A spoofed config can at most disable the feature or enable it where the chain rejects. Vizor therefore also requires the chain ProtocolCapabilities and VK fingerprint, but a RoundAuthPayloadV3 covering features would be cleaner.

## open_questions_for_owner
- Should the estimated delegation count (about revealed shares/16, public on-chain anyway) appear anywhere in Vizor? Recommendation: only on the delegate's own dashboard, labelled approximate. Never in the directory, profile ordering or search, to limit herding and leaderboard dynamics.
- Should Keystone/Ledger account holders be able to become delegates in v1? Recommendation: no. Ship software-account-only delegates, since the DK is a hot key either way. Add a random-DK-plus-backup-phrase path later if influencers ask.
- Is losing delegation visibility after reinstall or seed restore acceptable for v1, given the delegation still counts? Recommendation: yes, with explicit disclosure before confirming. Revisit an OVK-keyed recovery receipt (a protocol change) if users complain.
- How should Featured be ordered and curated? Recommendation: weighted-random per device and round for Featured, published criteria, and a disclaimer that Featured is not an endorsement of votes.
- Should profile photos of non-Featured delegates appear before human review? Recommendation: no. Show identicons until pfp_status is approved, to pass App Store 1.2 review and reduce impersonation via photos.
- Should there be any delegation cutoff before vote end? Recommendation: none beyond the 10-minute submission guard, with a 24-hour warning that shows each chosen delegate's voting progress. Late, informed delegation is a feature.
- Beta plan: should the first release run only on [TEST] rounds for one full round cycle before mainnet rounds? Recommendation: yes, with the remote flag fail-closed during beta.
- Who handles delegate reports, and what is the response target? Recommendation: Valar/Vizor support, with a 24-hour target for impersonation and offensive-photo reports and same-day delisting for confirmed impersonation.

## risks
- Users misunderstand finality or abstain-on-no-vote and blame Vizor when a delegate does not vote. Mitigation: a required checkbox, C1/C2 copy on the review and status screens, and per-proposal 'Didn't vote' states.
- Impersonation through lookalike handles or display names, or a stolen X account rotating the DK mid-round. Mitigation: lookalike warnings, fingerprints, 'New this round' and 'Key changed' labels, the chain cross-check at review, and contract C8 cooling-off.
- The delegate DK is a hot key on a phone that controls one-shot public routes for potentially large pools. Compromise permanently mis-votes the pool for that round. Mitigation: re-auth before signing, a rotation flow, and the recommendation that large delegates use a dedicated device.
- IP and timing linkage. Status polling, profile views and the proxy tx come from the same IP. Mitigation: whole-round route lists, decoy keys in IAVL verification, a thumbnail pack, and a Tor recommendation. This is still not PIR.
- A delegate who casts a private vote and public routes close together from one IP links their private VAN participation to their public identity. Choices stay hidden.
- Long helper delays (up to the last-moment window, randomized by as much as about 100 h) make share progress look stuck for days. Mitigation: C7 copy and an 'on track' state.
- Registry service or verifier outage blocks new delegations and onboarding (fail closed by design). X API or policy changes may break X verification; the GitHub and domain fallbacks must work at launch.
- App Store or Play rejection over user-generated profile content. Mitigation: report, hide, approved-only photos and text, published contact, and Featured curation.
- Version skew between the chain VK, the client VK and the config disables the feature silently (it fails closed). It needs release coordination and a debug diagnostic.
- The ZKP4 proving key adds app size and memory on low-end Android. There are no mobile benchmarks yet.
- Mixed batches can exceed tx size caps if the SDK does not split them, causing late, post-proof failures.
- Herding and vote-market concentration around popular delegates. Mitigation: weighted-random ordering and no public counts in the UI, but pooling remains inherently attractive to markets.
- Partial counting when some DC shares miss vote_end_time (helper failures), which is the same exposure as votes today and is surfaced in the status.
- Old Vizor installs on the same seed show 'Already used for this round' after a proxy delegation, which is correct but unexplained there.
